Equity-OS: what is being built, stage by stage

An explainer for the owner. Every statement is taken from the repository as of 2026-10-16 (specs, roadmaps, plans, code, config, tests and git log). Anything inferred is marked (inferred). Company examples use Apar Industries (the development company) and the watchlist companies already named in the docs.

TL;DR
  • What: a research back-end for Indian listed companies. It reads the same financial figures from up to six sources, keeps every original byte, compares the sources line by line under fixed rules, and only lets cross-checked first-party numbers become "facts". Reports and long-term memory are then built on those facts, and every number in a report must cite one.
  • Why it matters: the eventual product is a quarterly earnings-review workflow where you can trace every number to a filing and see where the sources disagree. The back-end is "complete" only when a four-quarter Apar pilot passes on it.
  • Gotcha: PDF parsing works only for Apar. On 10 other companies' results PDFs it extracted nothing (0/10), so the onboarding of new companies (D6) deliberately leaves the PDF out. New companies are checked with exchange XBRL plus vendors, and the expected outcome is PARTIAL.

01 What is being built

The project's doctrine (.claude/project/brief.md): "SQL records what happened. Curated memory preserves what was learned. Deterministic code calculates implications. Agents investigate, challenge, and explain." The product is an evidence-governed research system, not a stock-picking chatbot. Language models never compute numbers. They draft prose and review work, and every figure comes from code.

The work is split into three parts (docs/backend-roadmap.md):

02 The end-to-end flow

Each box is a component. Green ones are built, amber is in progress, grey dashed is planned. Arrows show what each component hands to the next.

The ledger also takes comparison results and calculation traces directly as citations (COMPARISON, CALCULATION), not only facts. D8 adds a source, and D9 acts on the capture store. Both dashed arrows are planned.

How data moves between components (the "contract" between boxes)

Components talk only through three things (data spec, "Component boundaries"): occurrences, interpretations and the measurement key. The measurement key is a fixed grain of entity × canonical line item × exact period interval × basis (consolidated/standalone) × accounting framework × currency and value kind × dimension set (segment member, elimination basis, shareholding category…). Every adapter produces values at this grain, the comparator lines them up at this grain, and a report claim cites this grain.

Everything is append-only in PostgreSQL (the runtime database role can't UPDATE or DELETE). Corrections are new rows that name what they supersede. Raw bytes stay in the file-based snapshot store and are referenced by SHA-256.

03 Every component, in order

Each card follows the same pattern: purpose, input, processing, output, handoff, limits and status. Deep detail is in the collapsible sections.

Sources and raw capture done · D1a/D1b

Purpose
Fetch documents from each authorised source and keep the exact bytes forever (until D9 adds retention), with a hash and a first-seen time. Nothing is parsed at this point.
Input
  • NSE XBRL instance (SEBI Integrated Filing, Ind AS): https://nsearchives.nseindia.com/corporate/xbrl/…xml, found through the NSE integrated-filing-results listing (and the legacy corporates-financial-results listing for older in-bse-fin filings).
  • Results PDF (the outcome-of-board-meeting PDF). For Apar these are retained as nse_pdf/APARINDS-FY26_Q2-results.pdf and similar files. Transcripts are retained too.
  • Screener consolidated company page https://www.screener.in/company/<SYM>/consolidated/ (logged-in session).
  • Tijori financials page https://www.tijorifinance.com/company/<slug>/financials/.
  • Upstox https://api.upstox.com/v2/fundamentals/<ISIN>/income-statement?type=consolidated&time_period=quarterly&fs=true (bearer token) and the public instrument file complete.json.gz.
Processing
Before any request, the source catalog checks that the source and surface are registered with a role and a retention authority (the rights records are A05-DECISION-004 for exchanges, A05-DECISION-005 for Screener/Tijori subscriber use, and the Upstox rights record §7). An unregistered surface gives NOT_AUTHORISED. Each fetch is recorded as an acquisition attempt with an outcome (COMPLETE, NOT_PUBLISHED, PARTIAL, FAILED, NOT_AUTHORISED, IDENTITY_REJECTED, UNSUPPORTED_SCHEMA, PARSE_FAILED), including failed ones.
Output
A capture record plus a content-addressed body in the snapshot store, for example data/raw/snapshots/v1/tijori/financials/apar-industries-limited/<timestamp>-<hash>/body.bin. Filing bundles have a retrieval-manifest.json recording URL, SHA-256 and NSE filing time per file (data/raw/watchlist/aparinds/). The data/raw/ folders include watchlist/ (one folder per development company plus screener-financials/), snapshots/ (blobs, tijori, upstox), upstox/, onboarding-dev/ and news/.
Handoff
The extraction adapters read the retained bytes, never the live web.
Limits
Vendor pages and Upstox carry no publication time, so their "knowledge time" is UNKNOWN and they count only from when they were captured. Nothing is scheduled: there's no market-wide or unattended capture (a register deferral).

XBRL extraction (the main first-party source) done · D1a

Purpose
Turn an exchange XBRL filing into a lossless list of "what the filing said", one record per fact.
Input
An NSE XBRL instance file. Three schemas are supported, each identified by its namespace URI rather than its prefix: the SEBI in-capmkt 2025-01-31 taxonomy (mapping xbrl/v1), the 2026-01-31 taxonomy http://www.sebi.gov.in/xbrl/2026-01-31/in-capmkt (mapping xbrl/v5, added for Apar Q4 FY26 and Q1 FY27), and the older BSE in-bse-fin (mapping xbrl/v3). The entry point declares the industry type. For a non-financial Ind AS company it's http://www.sebi.gov.in/xbrl/IntegratedFinance_IndAS/<date>/in-capmkt/in-capmkt-ent. Banks, NBFCs and insurers use IntegratedFinance_Banking, _NBFC and _LI.
Processing
Parsed with lxml (extract/xbrl_parser.py, evidence/xbrl_adapter.py). The adapter keeps every numeric and text fact, and a nil fact becomes NIL. Values stay as filed: XBRL amounts are already in rupees, so the raw scale is 0. The decimals attribute gives the precision (for example decimals=-5 means "to the nearest 1 lakh"). The period, scope (consolidated/standalone) and dimensions (such as segment members) come from the fact's context. An unknown taxonomy is refused as UNSUPPORTED_SCHEMA rather than read on a best-effort basis. Identity is checked too: the filing's ISIN, company name and context identifiers (NSE symbol scheme, BSE scrip scheme) must match the expected company. Otherwise the result is IDENTITY_REJECTED.
Output
Occurrences such as native_field=Expenses, context OneD, raw value with decimals=-5 (Apar Q2 FY26: 5,402.29 crore). They are later interpreted through about 124–132 mapping entries per taxonomy into canonical ids like revenue_from_operations and profit_before_tax.
Handoff
Interpretation (dictionary plus mappings), then the comparison run. XBRL is the representative first-party value when present.
Limits
Mappings exist only for non-financial Ind AS issuers. Some Apar folding and tagging quirks stay ANOMALY or UNMAPPED (for example the owners/NCI split in the 2026 filings, whose meaning isn't evidenced). Legacy in-bse-fin filings carry no ISIN.
Status
Built in D1a, extended in D1b, and 2026 taxonomy added as mapping set v5 (PREP-1). The extractor version is pinned (XBRL_EXTRACTOR_VERSION).

Results-PDF extraction (the second first-party representation) done for Apar not general

Purpose
Read the same filing from its printed PDF, so it can be checked against the XBRL. This is the "extraction check": it proves the reading is consistent, not that the filing is correct.
Input
A retained results PDF. For Apar Q2 FY26 that's APARINDS-FY26_Q2-results.pdf (sha256 8be1b8de…), with the consolidated P&L on page 3, segments on page 4, the balance sheet on page 6 and the cash flow on page 7 (Stage 1 manifest). An issuer config (config/aparinds-fy26-q2.yaml and the other quarters) adds the printed unit, label overrides for garbled text and unit-marker variants.
Processing
  1. Library: PyMuPDF (pymupdf) reads the PDF's text layer as words with coordinates (ingest/pdf_source.py). The new path runs no OCR. The older pipeline has an OCR recovery module using rapidocr.
  2. Find the statement page for each family (P&L, balance sheet, cash flow, segments). A page qualifies when it contains the basis marker, a title marker and every confirmation phrase as exact token sequences, with no fuzzy matching (extract/pdf_statement_pages.py).
  3. Bind columns to basis: consolidated and standalone columns are often printed side by side, so each numeric column belongs to the one super-header above it. A column under zero or two super-headers fails the family.
  4. Band rows by vertical position (4 pt tolerance) and keep each cell's raw text.
  5. Period comes from the column header text: a date (e.g. 30-Sep-2025) plus "quarter ended", "half year" or "nine months" gives the exact interval.
  6. Unit and scale come from each row's own unit marker (e.g. "Rs. in crores"), never from one value for the whole page. Garbled markers are declared per issuer as exact variants (Apar page 6 prints "Rs. in crones").
  7. Number grammar: Indian and international digit grouping, parentheses or minus for negatives, and the printed decimals give the precision. A dash becomes DASH (no value), an empty cell BLANK, a printed 0 ZERO_PRINTED. Anything else that doesn't parse becomes INVALID.
  8. Mapping by printed label: 126 entries in config/mappings/pdf/v1/results_layout.yaml, keyed to Apar's labels such as "1 Sales" and "3 Revenue from operations (1+2)" (which equals the XBRL value of 5,715.42 crore).
Output
One occurrence per banded row × requested-basis column, with anchor (page, line), raw text, unit context and missing-value state. Extractor version pdf-occurrences/2.
Handoff
Paired with the XBRL value of the same filing package in the comparison run (extraction status).
Limits
  • It only works on Apar. In the D6 capability probe (Q6), the generic, config-free path was run on 14 retained PDFs. For 10 non-Apar results PDFs (CGPOWER, ETERNAL, HFCL, LAURUSLABS, MTARTECH, NETWEB, POLYCAB, SONACOMS, THERMAX and TITAN, all Q3 FY25 BSE PDFs) it produced 0 occurrences on either basis. There are three reasons: identity is checked from a page-1 "Scrip Symbol :" line that only Apar prints; the P&L title must read exactly "Statement of financial results", while others print variants or no title; and the unit markers are Apar's exact strings, while others print "(INR crores)", "(Rs in Crore)" or "Rs. million".
  • Even for Apar, 17–97% of consolidated cells carry no resolved unit (Q2 17%, Q3 46%, Q4 36%, FY27 Q1 97%). The FY27 Q1 PDF declares no accounting framework. The Q4 FY26 revenue rows extract INVALID, an open item found in D1a and listed under PREP-1.
  • Ruling R-PDF (2026-10-16) followed from this: there's no generic PDF parser. During onboarding, RESULTS_PDF is always UNAVAILABLE with reason EXCLUDED_BY_RULE, and no PDF is fetched. A generic PDF parse is the follow-up bead eqos-yqi.
Status
Done for Apar (D1a, D1b). Generalising it is open (eqos-yqi).

Screener (independent vendor) company page done · D1b screen CSV planned · D7

Purpose
An independent second opinion on the filing's figures (corroboration). In D7 it will also supply the owner's own screen as a list of stocks.
Input
Company page (built): the authenticated consolidated page HTML, retained as data/raw/watchlist/screener-financials/APARINDS/consolidated/screener_financials_page.raw.html. Screen (planned, D7): a results CSV that you export from a Screener custom screen. The system will never call Screener's ?q= screen URLs itself.
Processing
Company page: four sections of the page are read: quarters, profit-loss, balance-sheet and cash-flow. Each table row × column header becomes one occurrence, TTM included. The mapping (31 entries in config/mappings/screener/v2/financials.yaml) covers these labels: Sales, Expenses, Operating Profit, Other Income, Other income normal, Exceptional items, Interest, Depreciation, Profit before tax, Net Profit, Minority share, Profit for EPS, EPS in Rs, Equity Capital, Total Assets and the three cash-flow totals. Precision is the displayed decimals at the displayed scale, so "5,250" means ±0.5 crore. Some vendor definitions are recorded as known traps: Screener "Expenses" excludes finance cost and D&A, "Other Income" = other income + exceptional items, "Total Liabilities" is the balance-sheet total and maps to nothing, and EPS is vendor-derived, so it's related to filed EPS but not equivalent. Identity and basis are checked: the page's company id and BSE/NSE codes must match, and a degenerate or standalone page is refused.
What's not pulled
The schedule expansions (the "+" drill-downs) aren't requested by the comparison. Any other row in those four sections is kept as an UNMAPPED occurrence. Other page areas, such as ratios, peers and shareholding, aren't part of the comparison ingest (inferred from the four-section rule; the older pipeline has separate Screener shareholding and segment readers).
Output
Vendor occurrences with knowledge time UNKNOWN. Screen (D7): a screen-run record with who ran it, when, the CSV capture and its members, each resolved to a universe-registry row or marked UNRESOLVED.
Handoff
The vendor side of corroboration pairs. A screen run feeds an owner-launched capture batch (D7), where each chosen member goes through onboarding (D6) and a comparison run.
Limits
A vendor value never becomes a fact. It enters a report only as a COMPARISON difference. Most mappings are still EQUIVALENCE_UNPROVEN, which means agreement shows as AGREE_UNQUALIFIED and disagreement as ANOMALY rather than MISMATCH.

Tijori (independent vendor) done · D1b

Purpose
A second independent vendor for corroboration.
Input
The financials page, whose data sits in an embedded JSON "island" (fin_tables_data). It's retained as body.bin in the snapshot store.
Processing
Only consolidated tables are read (qt_c, pl_c_*, bs_c_*, cf_c, fr_c). Each row × reporting-date column becomes an occurrence, nulls included. Only four mapping entries are selected: qt_c "Net Sales" (and qt_s), qt_c "Net Profit" and pl_c_s "Sales". Tijori's "Net Profit" maps to continuing profit after tax, never to profit for the period, and only when discontinued operations are zero. Its final date-labelled pl_* column is TTM, never a fiscal period. Precision was re-measured at displayed decimals (owner decision D4 withdrew an earlier 0.5-crore assumption).
Output / handoff
Vendor occurrences go to corroboration pairs.
Limits
Very narrow coverage (four mapped lines). Tijori shareholding is unverified: its only fixture is synthetic.

Upstox (diagnostic only) done · D1b

Purpose
A parse-check on our Screener reading, never a vote. Upstox values were shown to share Screener's upstream lineage (its operating profit equals Screener's PBT to the crore, 12/12), so they aren't independent.
Input
The income-statement JSON (a summary of 3-month points plus a full_statement of 12-month points, annual even on a quarterly request) and the instrument file used for identity.
Processing
Five mapping entries: summary revenue → total income, summary operating_profit → PBT incl. associates, and full-statement Revenue, Total Revenue and Profit Before Tax. All are unproven. Because Upstox precision is undocumented, Upstox pairs are NOT_COMPARABLE / PRECISION_UNSUPPORTED (owner amendment 2026-10-14).
Output / handoff
Diagnostic pairs that are shown in the report but never enter a status, trust, admission or run completeness. A disagreement routes MEDIUM PARSE_CHECK_DISAGREE.
Limits
An Upstox failure never makes a run INCOMPLETE.

Canonical dictionary and mappings → interpretations done · D1a

Purpose
One list of every financial line item, so that "revenue" means the same thing from every source. Each source is mapped into it once per surface and schema version, never per company.
Input
Occurrences, the dictionary (config/dictionary/v1, v2) and a mapping set (config/mappings/v1…v5.yaml). Mapping set v5 = XBRL (both in-capmkt taxonomies and in-bse-fin), PDF, Screener, Tijori and Upstox entries, plus "constructions" (vendor formula rows).
Processing
Each occurrence is matched by its selector (element name, or label plus section) to a canonical id, then normalised to exact base-unit decimals with its sign convention, given an uncertainty interval (value ± half its declared precision) and an evidence tier. Derived rows (OPM, EBITDA excluding other income, PBT margin, effective tax rate, opex_excl_finance_and_da) are computed by a formula engine with exact rational arithmetic, half-even rounding and outward-rounded bounds, and each stores a calculation trace. Applicability is decided before any value is looked at. For example, balance-sheet rows are NOT_APPLICABLE for a Q1 or Q3 package that has no balance sheet. Nothing is zero-filled.
Output
Interpretations at the measurement key. The resolved v1 dictionary has 259 rows (P&L 53, balance sheet 68, cash flow 96, segment 20, shareholding 4, derived 18; docs/specs/artifacts/dictionary-v1-manifest.md). Unmapped native lines are kept as UNMAPPED and queued LOW as candidates for addition.
Handoff
The comparison run.
Limits
The dictionary covers non-financial Ind AS issuers only. Two PBT concepts are kept on purpose: profit_before_tax (before associates, used for the tax rate) and profit_before_tax_incl_associates (the headline). For Apar Q2 FY26 these are 340.56 and 340.53 crore.

Comparison run, report and review queue done · D1a/D1b

Purpose
For one company, period and basis, line up every source's value per line item and give each line two separate verdicts: extraction (XBRL vs PDF) and corroboration (first-party vs vendors). There's no blended score. Full rules are in section 04.
Input
Interpretations, the selected filing package (latest eligible at the cutoff, with corrections superseding originals), acquisition attempts, and pinned versions of the dictionary, mappings, normalisation, rounding, definition set and comparison policy. Command: fundamentals compare run --entity <key> --period-end <date> --basis consolidated --mode as_known …
Output
An immutable run manifest (cutoff, mode, every pinned version, the code commit, exact input ids and capture hashes, attempts including failed ones) plus one result per applicable line: the source-state vector, pair outcomes with difference and gap, extraction status, corroboration status, and queue items. The run status is COMPLETE, or INCOMPLETE with its listed operational failures. The CLI exits with one of: success, success with open HIGH items, INCOMPLETE, or failure. fundamentals compare report prints it all.
Handoff
The queue (dispositions by the approval panel), admission to facts (D2), and ledger citations (D3).
Limits
A run is reproducible from its manifest alone (replay). Queue dispositions never edit a result; their effect appears only in a new run that pins a new definition set or mapping. Stage 1 acceptance covered Apar plus nine watchlist companies (SONACOMS dropped, eight of them XBRL-only), matched to a hand-verified frozen manifest.

Fact store and admission done on test DBs · D2

Purpose
Move the older SQLite fact store into PostgreSQL losslessly and decide which compared values become facts.
Input
The legacy SQLite fact-store files (config/legacy_import_manifest.yaml) and comparison run results.
Processing
The import is checked by counts, per-row hashes and selection digests. An admission rule then applies: only a first-party value whose extraction is AGREE (or NOT_APPLICABLE for single-representation families), with no open non-diagnostic HIGH queue item, is admitted. Vendor values never are. The phase also builds cutover with a frozen window and rollback, and a matched backup (pg_dump plus a capture archive) with a restore test.
Output
Fact rows plus an admission record (run id, result id, interpretation, occurrence, queue-overlay position). The Apar Q2 FY26 consumer report from facts shows filed tax 88.83, ETR 26.08%, headline PBT incl. associates 340.53 and PAT 251.70 crore. Tax is never computed as PBT − PAT.
Handoff
FIGURE citations in the report ledger.
Limits
Done and rehearsed on test databases only. The production cutover of the real database is the owner-gated bead eqos-3zl and must happen before the pilot (PILOT-3).

Report ledger done on test DBs · D3

Purpose
Store reports, approvals, the Q0 thesis and the management ledger as append-only database rows, with every number in a report checked against the stored figure it cites.
Input
Drafted report versions (sections in Markdown with placeholders, plus one typed row per numeric claim). Imports come from config/ledger_import.yaml: Apar earnings updates FY26_Q2–FY27_Q1 (data/reports/aparinds/<period>/earnings-update.{md,json}), the Q0 thesis (docs/evidence/phase-0.5/q0-approved-thesis.md plus its YAML twin) and data/ledger/aparinds-management-ledger.json.
Processing
  • Numbers appear in text only as placeholders {{c:<claim key>|<style>}}, rendered deterministically from the typed claim. A bare analytical numeral blocks submission (UNREGISTERED_NUMBER).
  • Each claim has one citation: FIGURE (fact or interpretation + run), CALCULATION (trace), SOURCE_QUOTE (verbatim quote at a capture anchor, used for guidance), COMPARISON (a cross-source delta) or POLICY (an owner-set threshold).
  • The claim check gives each claim MATCH, MATCH_UNTRUSTED, POST_CUTOFF, UNIT_MISMATCH, KEY_MISMATCH, VALUE_MISMATCH, QUOTE_NOT_FOUND, QUOTE_MEANING_MISMATCH or UNRESOLVED.
  • Lifecycle: DRAFT → SUBMIT (content sealed by SHA-256) → IN_REVIEW → the approval panel (one configured model reviewer, run only after the deterministic checks pass) gives APPROVE, REQUEST_CHANGES or REJECT. The owner can override. A correction is a new version that supersedes the old one.
Output
Report, version, section, claim, validation, panel-review and decision rows, each decision chained by digest. Examples from the Stage 1 test: FY27_Q1 revenue 6,591.06 is POST_CUTOFF under a retrospective check, and a corrective version with an honest cutoff gives MATCH. The Q0 falsifier F1 11.55 is a self-cited POLICY claim (MATCH). FY26_Q3 cables growth displays as "**20%**". fundamentals ledger export reproduces every imported version's content hash byte for byte.
Handoff
Memory supports (D4) and views (D5).
Limits
Imported Apar updates are HISTORICAL, not approved. Non-numeric claims stay prose until register item B-06 freezes a claim schema. A drafted quote's guidance contract binds only through a sealed import (open bead eqos-0eu). There's a SQL-level SUBMIT hash gap, bead eqos-7pr.

Long-term memory done on test DBs · D4

Purpose
Keep short, supported statements per stock that persist between quarters. They're promoted only by a separate decision, so approving a report never silently changes memory.
Input
A staged candidate item (kind, statement, validity interval) plus at least one support: an approved version, a MATCH claim, a definition record, a queue disposition, a decision or a capture. The kinds are COMPANY_UNDERSTANDING, MANAGEMENT_TRACK_RECORD, THESIS_AND_WARNING, SOURCE_QUIRK, OWNER_RULING and LESSON.
Processing
A support predicate is checked when the item is staged and again inside the PROMOTE transaction, with locking against concurrent withdrawals. The status runs CANDIDATE → PROMOTED → RETIRED. An item derives NEEDS_REVALIDATION if a support later fails. Search uses PostgreSQL full-text search, and retrieval is "as known at a cutoff".
Output
Example from the Stage 2 test: an Apar MANAGEMENT_TRACK_RECORD on cables EBITDA margin (9.5–10% guided in FY26_Q3, 10–11% in FY27_Q1), supported by both quote claims, is returned by MemoryStore.retrieve("cables margin", stock=Apar, cutoff=…) only after a panel PROMOTE.
Handoff
Views (D5). In future, drafting agents read it in the earnings-review workflow (PILOT-5).
Limits
The comparator and claim check never read memory. Vector search is deferred until measured. Evidence-layer knowledge-time gaps are parked as eqos-d60.

Generated views done on test DBs · D5

Purpose
Read-only Markdown for people. Nothing flows back from the views.
Input → output
fundamentals ledger export --stock … writes each sealed narrative (hashing to its content hash), one status note per report (derived status, decisions, latest validation, untrusted claims, revalidation flags) and the promoted memory per stock. A database role, eqos_reader, can SELECT two status views and write nothing.
Limits
The optional Obsidian vault (D5.3) was not built (ruling V1). The dashboard tool is deferred.

Coverage model: universe, screens and watchlist planned · D7

Purpose
Three nested sets. A universe registry of about 5,000 listed stocks holds identity only. Stocks that come out of your screen are captured and compared on demand. Your watchlist (about 50–200) are the only stocks that get reports.
Input
The Upstox instrument list (registry refresh, identity-only role), a CSV you export from a Screener custom screen, and your ADD/REMOVE decisions with a verbatim reason.
Processing
A registry reload is idempotent, and an ISIN seen under a new symbol records only a candidate identity event. A screen run resolves CSV members to registry rows. A capture batch over the members you choose onboards (D6) and compares exactly those, and nothing is scheduled. Watchlist decisions are owner-only. Drafting for a stock that isn't on the watchlist is refused, and a new member's first report must be a BOOTSTRAP_THESIS.
Output
Registry rows, screen and screen-run records, batch results, and a per-stock watchlist decision chain.
Limits
The ten "watchlist companies" used for development are a comparison set, not the product watchlist. None is on the watchlist without an owner ADD.

Shareholding filing source planned · D8

Purpose
Add the exchange shareholding-pattern filing as the first-party source for promoter, public and institution holdings, compared against Screener and Tijori (Upstox as a diagnostic).
Processing
The source is registered in the catalog before any capture. The value is an instant (the shareholding date). The category hierarchy is versioned per regulatory format. The denominator (total shares, voting rights, or promoter holding for pledge %) and share class are part of the key, so values on different denominators are never paired. Vendor "Public" maps only to the matching aggregate. Holder drill-downs are THRESHOLDED, and an absent holder is unknown, never zero.
Output
Shareholding occurrences and comparison rows. The exit test shows Apar's promoter, public and institution aggregates against each vendor.
Limits
The extraction check applies only if the filing has two representations, which will be settled at the start of D8.

Retention and replay planned · D9

Purpose
Make storage grow with coverage, not with the whole market.
Rules (ledger spec O9)
Kept forever: filing figures, reports, approvals, memory, comparison outcomes and covered stocks' exchange originals. Other results PDFs and XBRL are deleted three months after verification (the address and hash are kept, and a re-fetch must hash-match). Vendor pages are kept for four quarters plus any open-review hold, and purged at licence end. Purges run only on an explicit command, with a dry run first, and are never scheduled.
Output
Retention classes, holds, tombstones, re-fetch outcomes (RESTORED or REFETCH_MISMATCH), and replay reporting ORIGINAL_EXPIRED for expired vendor captures.
Limits
The roadmap rates this a deep-risk phase because it physically deletes evidence under concurrency.

Grain: one measurement key, meaning the same entity × canonical line item × exact period interval × basis × framework × currency/kind × dimensions. Different periods, bases, frameworks or dimension members are never paired. They come out as NOT_COMPARABLE with a reason.

The tolerance rule

Every value carries an interval of value ± half its declared precision. For XBRL the precision is the decimals attribute, for the PDF the printed decimals at the printed scale, and for vendor HTML the displayed decimals. A vendor API with no documented precision is PRECISION_UNSUPPORTED. Derived values propagate intervals by interval arithmetic, with bounds rounded outward. Two sides agree if and only if their intervals overlap. Precision is never invented, and exact counts are single points, so adjacent integers never agree.

When sides don't agree, triage applies: STRUCTURAL for a ×10/×100/×1000 factor or a sign flip, MAGNITUDE for a relative difference ≥ 0.5% (comparison policy v1, which replaced the old comparator's 20%), and otherwise NOISE.

05 Identifier-only onboarding (D6), in plain terms

What "give it only an NSE symbol" means

Today every company in the repo was set up by hand: a config file per quarter (config/aparinds-fy26-q2.yaml), declared units and an identity file. D6 removes that. You type fundamentals onboard <SYMBOL>, and the system discovers the company's ISIN, BSE code and filings and the matching vendor pages by itself. It checks that they are all the same company, works out the settings from the filings, ingests what it could verify, and prints the exact comparison command. The comparison then has to work with no code or configuration change. The point is that adding company number 11, or company number 500, shouldn't need an engineer.

The core risk: getting identity wrong silently attaches figures to the wrong company. Every step therefore fails closed. The system never guesses a vendor slug, never picks one of several candidates, and never infers a rename. Anything it captures during discovery stays "identity evidence" and can't be compared until its unit is verified.

Why financial-sector companies are refused

Banks, NBFCs and insurers file different statement formats, and the dictionary and mappings cover only non-financial Ind AS issuers (data spec "Out of Scope"; bead eqos-hvh for the bank row set). The refusal is fail-closed: a company is supported only if it shows a positive non-financial signal. The signal pinned in Task 0b is the XBRL entry-point namespace …/IntegratedFinance_IndAS/<date>/in-capmkt/in-capmkt-ent, which every one of the 11 development companies carries. The bank (HDFCBANK), NBFC (BAJFINANCE) and life-insurer (HDFCLIFE) samples carry _Banking, _NBFC and _LI instead. Anything else, or a missing namespace, gives UNSUPPORTED (FINANCIAL_OR_UNKNOWN_SECTOR). The schemaRef file name was rejected as a signal because banks use the same one.

Temporal identity: renames and symbol events

Identifiers change over time. ETERNAL, for example, was formerly ZOMATO, and the repo already carries that rename as a legacy registry alias. Task 2 (migration 0022_identity_events.sql, entity/identity_layers.py) adds:

  • Identifier relationships with a valid-from date and evidence, attaching an ISIN to a security and an NSE symbol or BSE scrip to a listing.
  • Identity events that end or start relationships, never inferred from data: ISIN_CHANGE, SYMBOL_CHANGE, SYMBOL_REUSE (only after the old holder's relationship ended), MERGER, DEMERGER and DELISTING.
  • A latest_slice(as_of) view that gives the identity valid on a date. With no events it returns exactly today's seeded values, so existing companies are unaffected. A filing is checked against the identity expected on its filing date, so a pre-rename filing still verifies after a rename is recorded.

Stable internal entity, security and listing ids never change. Re-onboarding after a rename resolves to the same ids. Task 2's code is currently being written by another worker and isn't committed yet.

Derived settings

Settings are read from the verified XBRL, never typed by hand, and each one cites its discovery evidence: fiscal year end (from DateOfEndOfFinancialYear), rounding level (LevelOfRounding), presentation currency, framework (Ind AS from the entry point), basis status (consolidated-and-standalone from the filing listings) and document locations (URL plus SHA-256 per ingested instance). Each setting has a valid_from, so a change such as a new fiscal year end governs only later periods and never rewrites stored observations. For Apar the expected values are fiscal year end March, CONSOLIDATED_AND_STANDALONE, INR and Ind AS.

The held-out company discipline

To prove onboarding works on a company nobody tuned the code for, one company was chosen before any D6 code was written, and it is kept out of all development files:

  • Seeded draw. The frame was the NSE Nifty 500 list with Financial Services excluded. Every company whose symbol, ISIN or name appears anywhere in the repo's history, untracked files or data folders was also excluded. The start index is sha256(seed_commit : frame_sha256 : attempt) mod the universe size, and the draw walks forward to the first candidate that passes the eligibility rules (EQ series, Indian ISIN, at least two consolidated integrated filings, exactly one BSE match). The seed proves the choice wasn't steered. It doesn't make the choice secret.
  • Hidden until the run. The symbol appears only in stage4_holdout.yaml and the future Stage 4 manifest. A leak scan (Task 1b) checks every git object and untracked file under src/, config/ and tests/. Checks fail opaquely, never printing the value, and any disclosure before the freeze "burns" the attempt.
  • Predicted outcome: PARTIAL, run INCOMPLETE, excluded exactly RESULTS_PDF. This is computed from the committed capability table, where every unit is reachable except RESULTS_PDF: {excluded: R-PDF}, so it's the same prediction for any candidate. A different result is a failed attempt, followed by a fix under a bead, a new freeze and a new draw. The prediction is never revised.
  • Implementation freeze. After review, a descriptor commit pins the code. The final test asserts that nothing under src/ or config/ changed between the freeze and the run.

Attempt history: the first draw ran out of candidates at 3, because two whole-market Upstox instrument maps in scratchpad/ matched nearly every company. An amendment (approved 2026-10-16) exempts exactly those two files by content hash. Nothing had been selected, so nothing was burned. Attempt 1 was then drawn and committed with reviewer approval (9e7d407).

Deep detail: acquisition, replay and the eligibility gate
  • Every onboarding writes an immutable generation <raw-root>/gen-<n>/ with a discovery-manifest.json (each request's key, URL, SHA-256, time and outcome, failures included), a retrieval-manifest.json (XBRL only) and an acquisition.json tying it to the freeze commit. Replay reads only these files, never opens a network socket, and gets the same outcome even with the clock moved three years ahead.
  • An eligibility gate at the database insertion point refuses any occurrence from an identity-only surface, or from a capture linked to discovery unless its unit was verified in an ONBOARDED/PARTIAL record. Captures from an attempt that later hit a conflict therefore stay ineligible.
  • The PDF exclusion is written as a capture-less acquisition attempt with outcome EXCLUDED_BY_RULE. Without it the run would wrongly read the PDF as "no value" and report COMPLETE. That case is a negative-control test.
  • Onboarding pins ONBOARDING_VERSIONS = dictionary v2, mapping set v5, because the CLI defaults (v1) can't read the 2026 taxonomy.
  • Follow-up beads: eqos-yqi (generic PDF), eqos-9sn (vendor identity date), eqos-g2q (symbol reuse for an issuer not yet onboarded).

07 Glossary

Occurrence
What one source literally said for one cell: raw text, unit, scale, anchor (page/line, XBRL fact, JSON path) and capture hash. Immutable.
Interpretation
An occurrence mapped under a named mapping version to a canonical line item, with a normalised value, an interval and an evidence tier.
Measurement key
The comparison grain: entity × line item × exact period × basis × framework × currency/kind × dimensions.
Canonical dictionary
The versioned list of every financial line item (259 rows in v1) with meaning, kind, sign, applicability and formulas.
Evidence tier
EQUIVALENCE_DEMONSTRATED (measured on at least 5 companies including a discriminating case), RELATED_NOT_EQUIVALENT, or EQUIVALENCE_UNPROVEN. Only demonstrated mappings can produce AGREE or MISMATCH.
Extraction check
XBRL vs PDF of the same filing: consistency of reading.
Corroboration
First-party vs independent vendors (Screener, Tijori).
Fact
A first-party value admitted after extraction AGREE with no open HIGH item. Append-only and revision-aware.
Claim
A typed number in a report with exactly one citation (figure, calculation, quote, comparison, policy).
Approval panel / owner role / runtime role
One configured model reviewer decides after deterministic checks. The owner records verbatim rulings and can override. Drafting agents can only insert drafts and SUBMIT.
Memory promotion
A separate decision that lets a supported statement into long-term memory.
Run manifest
The immutable record of everything a comparison run used. Replay uses only this.
Frozen manifest
Expected results hand-verified from source documents, reviewer-approved and committed before the end-to-end test that must match them.
Verification unit
One source whose identity onboarding verifies separately (EXCHANGE, XBRL_ENTITY, SCREENER, TIJORI, UPSTOX, RESULTS_PDF).
Onboarding outcome
ONBOARDED, PARTIAL, IDENTITY_CONFLICT or UNSUPPORTED.
Held-out company / attempt / freeze
The company drawn before D6 code was written and kept out of development; one pre-registered draw and its prediction; the committed code revision that must not change before the run.
Valid time / knowledge time / cutoff
When a figure applies; when it became public; the time a run or check is "as of". AS_KNOWN mode reproduces exactly what was known then.
Consolidated / standalone basis
Group accounts vs the parent company alone. The two are never compared with each other. Onboarding supports consolidated only.
