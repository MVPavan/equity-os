## 3. Minimum proposed installation, database and build contract (I3)

All contracts here are proposed for independent review and exact-byte acceptance, not facts about an installed system.

### Stable installation and existing-only read path

Trusted root supplies a process-local `ProducerInstallationContext`: operator-assigned logical `database_id`, expected immutable `installation_id`, expected installation-record digest, protected parent/directory/file handles for the active database and sibling ledger, supported fact-schema fingerprint, accepted producer-contract bytes/digest and independently vetted build manifests. It has no caller timestamps or imported associations. Source intake anchors are consumed separately; they do not automatically identify this database. An ID/path read from the ledger cannot establish its own authority.

The external immutable `ProducerInstallation` contains exactly the common fields in §4 plus `installation_id` (operator-generated UUID), `database_id` (operator-assigned logical ID), `ledger_id` (fresh UUID), `fact_schema_sha256` (digest of exact supported schema descriptor bytes), `producer_contract` (complete accepted bytes/digest), and `installed_at` (actual UTC). Its identity stays stable across approved parser builds. The trusted root retains its expected digest and runtime anchors outside untrusted source/argv/config input. Do not store changing device/inode values in the portable canonical record: root pins and checks them in the runtime context on every open. Adding this external record never edits the old fact database header or schema.

Ordinary `open` requires an existing ledger/installation and existing database. Compare all installation fields against independently supplied root bindings; validate protected ancestry, file identity, owner/modes, schema descriptor and exact referenced rows. Missing/mismatched binding refuses without creating, migrating or repairing anything. A ledger copied to another database or directory fails the root's independently pinned pair, even if row IDs/digests match. Same-account arbitrary administrator rewrites remain outside the threat boundary.

`ExistingFactReader.open_existing(context)` lives in the new proof-store module and opens SQLite existing-only `mode=ro`, sets `query_only`, and uses a consistent read transaction. It never calls `FactStore.__init__`, `_init_schema` or legacy-selection migration. It validates the known schema through read-only metadata, then reads complete raw columns. This minimum reader supports the existing UTF-8 rollback-journal database only: inspect its pinned header before SQLite open, refuse WAL-mode headers, hot journals or unexpected sidecars instead of creating/recovering them. Supporting an active WAL database requires a separately reviewed existing-sidecar read contract; do not change its journal mode. Do not use SQLite `immutable=1` on a changing active database. Proof preflight occurs before any new normal FactStore construction. For a live write, consume an already opened accepted active store only after preflight; its existing construction is outside the proof-reader no-write claim. Archives are never opened with the normal constructor by this path.

**SQLite protection and durability:** Protected directories are operator-owned 0700; database/ledger/lock/sidecar files are regular, operator-owned 0600, with no symlink components or group/other writes. Root pins parent/directory descriptors and database file identity; verify ancestry and identity before/after each SQLite open and before publication. Python stdlib SQLite is not a descriptor-relative VFS: the protocol requires stationary protected ancestry and excludes noncooperating same-account filesystem replacement. Do not claim intake no-follow file reads automatically protect SQLite's path opens. Refuse unsupported protection/filesystem guarantees.

Only the new ledger uses explicit `journal_mode=DELETE`, `synchronous=FULL`, checked foreign keys and append-only records/triggers, one bounded operator-store lock and SQLite write transactions. Verify actual pragma values; unsupported mode/flush/lock fails closed. After commit, fsync the ledger file and containing directory, and every newly created parent entry child-before-parent before reporting durable publication. SQLite owns journal commit/sync ordering; do not manually unlink journals or alter the fact database's pragma policy. Row observation proves visibility of a committed row, not a newly guaranteed power-loss durability outcome for the existing writer. Cross-database atomicity is not claimed.

Restore is an explicit future operator operation: restore the exact matching database/ledger pair, verify installation identity and every referenced row, then independently re-anchor runtime handles while preserving logical IDs and immutable record bytes. Ordinary reopen neither recreates installation nor declares a restore successful. A bare database copy cannot acquire proof.

### Build lifecycle

Retain one immutable `ProducerBuildManifest` per vetted build: common fields plus `build_id`, `producer_version`, `runtime_version`, `artifact_entries` and `build_acceptance` (complete engineering acceptance bytes/digest). Each artifact entry has exactly `logical_name`, `kind` (`code`, `runtime`, `configuration`), and an opaque byte envelope. Entries are unique/sorted by logical name. Cover invoked extraction, parsing, normalization, identity/reconciliation, configuration interpretation and proof-writing modules; Python executable/runtime and loaded relevant library/native artifact bytes; exact resolved defaults/registry/semantic configurations. A HEAD hash, worktree digest, version string or package-version list alone is insufficient. No dependency installation is proposed.

Root verifies actual installed artifacts against the vetted manifest at composition/open, before execution and before association publication; code/config is pinned read-only for the execution and only declared imports/artifacts may participate. Changes or undeclared execution artifacts refuse proof. Each association references its own exact build manifest; approved upgrades append a manifest and leave installation identity and old evidence unchanged. Historical reads verify retained manifest/code/config bytes without rerunning or requiring that old build to be active. Missing historical build bytes refuse complete association verification; never replace them with the current manifest. Domain acceptance is not conferred by build vetting.

## 4. Lossless records and comparison contract (I4)

### Exact bytes, profiles and fields

New metadata uses **`eos-producer-json-v1`**, importing S10 `eos-manifest-json-v1` rules 1, 2, 4 and 5, with a declared replacement for rule 3: arrays retain their declared order; set-like arrays must already be uniquely sorted as stated below and are validated, never automatically resorted. This is a proposed new profile, not a change to S10. Existing nested JSON is never recursively NFC-normalized, sorted or reserialized.

Every new record has required `schema_version=1`, exact `domain`, and `record_sha256`. All fields are present, unknown/duplicate fields refuse; only explicitly nullable fields below admit null. Hash preimage is ASCII domain plus one LF byte followed by canonical metadata JSON with only its own `record_sha256` member omitted entirely. SHA-256 is lowercase hex. Metadata stores padded RFC 4648 base64 opaque bytes; their base64 is canonical and digest/length are rechecked. IDs are ASCII tokens; operator UUIDs use lowercase standard UUID spelling.

An **opaque byte envelope** has exactly `payload_type`, `original_profile`, `bytes_base64`, `byte_count`, `sha256`. SHA-256 covers original bytes without a new domain prefix. Original bytes/profile remain unchanged, including Unicode spelling, positional dimensions, lexical decimals, nulls and exact stored JSON. New live Fact/Observation/check payloads are serialized once at their actual seam with the identified existing serializer/runtime profile, then that immutable buffer is retained and parsed only for validation/comparison. Unknown original profiles fail verification. Receipt and approved configuration bytes use their existing exact profiles; configuration source bytes and resolved effective bytes are separate envelopes. Closed supported original profiles for this release are `existing-model-json-v1` (UTF-8 of the existing zero-argument `model_dump_json`, with runtime pinned by build), `existing-sql-text-utf8-v1` (exact UTF-8 SQL TEXT bytes), `existing-intake-record-v1` (exact retained `canonical_json(receipt.model_dump(mode="json"))` plus its original LF; its existing own-digest preimage stays unchanged), `existing-config-source-v1` (exact source bytes), `existing-stable-json-v1` (the existing `_stable_json` UTF-8 output), and `eos-producer-json-v1` (new complete metadata records). No new normalization is applied inside any envelope.

| --- | --- |
| Installation / `EquityOS:ProducerInstallation:v1` | Fields declared in §3; no nulls. |
| Build / `EquityOS:ProducerBuildManifest:v1` | Fields declared in §3; artifact entries sorted uniquely by logical name; no nulls. |
| Stored row / `EquityOS:PersistedRevisionBytes:v1` | `installation_id`, `database_id`, `columns`, `fact_json`. `columns` contains every exact SQL member listed below; `fact_json` is the opaque UTF-8 byte envelope. No selection projection. |

Append separately; never mutate association. See §5; no writer/production success exists in this release. |

`columns` contains exactly `row_id`, `content_identity`, `value_hash`, `revision_family`, `revision_ordinal`, `canonical_status`, `canonical_selected_at`, `canonical_reason`, `source_id`, `file_sha256`, `anchor`, `valid_time_start`, `valid_time_end`, `knowledge_time`, `first_seen_time`, `created_at`. SQL integers remain integers; every TEXT value is a lossless UTF-8 opaque envelope rather than a normalized string. Only `canonical_selected_at`, `canonical_reason`, `valid_time_end` are nullable, exactly when SQL NULL. `fact_json` comes from the exact SQL TEXT bytes, not `StoredRevision.fact`; retain original `anchor` JSON too. Unknown/missing columns refuse. This digest identifies an observed row envelope, not its historical producer.

After restart, a complete retained association may be independently byte/protection/flush-verified as retained derivation/row-observation evidence; this never proves an earlier successful acknowledgment or final flush time. Missing/partial records are never completed or assigned old times on reopen. Source receipt bounds must be <= source cutoff <= run start; producer completions are >= their dependencies, nondecreasing and <= current actual verification time. Publication must follow row observation. Retrieval supplies a fresh actual `verified_at` in its runtime wrapper, distinct from immutable producer clocks. No production clock/import parameter; synthetic installations can control a module clock only. Naive/backward/future clocks refuse without clamping. Generate a new execution ID on rerun; restart never reconstructs an abandoned execution's completion.

## 5. Future selection extension remains disabled (I2, M3)

The association-only release has no callable `select_current` proof writer and no successful `query_produced_canonical`. Existing legacy selector/retrieval behavior remains compatibility behavior carrying recorded claims; even newly observed transitions stay uncertified here. Any reserved canonical-proof query returns typed `selection_proof_disabled`, never joins the latest association to the effective row.

Before a future extension is enabled, independently reviewed/accepted contracts must supply `ApprovedSelectionContext` from trusted root: complete approved reconciliation-policy bytes/version/digest; its distinct `DOMAIN_EXPERT_ACCEPTANCE` requirement/record/human-resolution bytes; complete closed event-mapping bytes/version/digest; applicable exact event/scope/evidence; and every resulting typed approval requirement, matching approval record and human resolution. Canonical-selection event mapping is unavailable in inspected S15; nearby human-review/memory-promotion contracts do not fill it. Do not implement S15 here.

Reserved future interface: `select_current(*, association, expected_selection_id, reason, selection_context: ApprovedSelectionContext)` must independently verify all bindings before calling the existing selector at an actual sampled time, then read back the exact committed transition/chain and append the separate final selection record in §4. `reason` is audit text only. `policy_context` must retain the complete policy, mapping, policy acceptance and their digests; `event_scope`/`event_evidence` must retain complete exact bytes. Each `required_approval_bindings` entry contains exactly `requirement_bytes`, `approval_record_bytes`, `human_resolution_bytes`; each includes its original digest/profile, and entries sort uniquely by requirement ID. Validate type, authority/source, actor, scope, timestamps, active/unrevoked/unexpired state and one-to-one matching IDs/digests, including `approval_id`, `approval_record_id`, `human_review_id`, `resolution_decision_id`, `resolution_content_sha256`. Missing/stale/wrong-scope authority refuses before selector mutation. Synthetic typed-capability/authority fixtures may prepare that contract; they are not production acceptance.

The future `selection_row` has exactly `selection_id`, `content_identity`, `row_id`, `sequence`, `predecessor_id` (nullable iff initial), `selected_at`, `reason`, `legacy_baseline`, `selection_sha256`; integer/TEXT encoding follows the row-envelope rules, retaining complete raw columns; `selection_digest_preimage` retains the existing `_stable_json` bytes/profile, including predecessor digest. Preserve old digests. The final record references the immutable pre-selection association digest and exact predecessor, never retrofits the association. A future query would determine the effective transition first and require its own exact completed proof plus eligible dependencies; it must refuse a missing proof without falling back to older proved transitions.

**Post-selection crash limit:** A crash after selector commit but before final proof durability can leave an effective unproved transition. Reopening does not finalize it. An unchanged rerun yields association-only evidence and still cannot satisfy `query_produced_canonical`; no artificial same-row reaffirmation or latest-association promotion repairs this. Characterize this exact legacy outcome now, and test publication failure if the future extension is separately accepted. Any proof-recovery transition requires a separately accepted successor contract outside this packet.
