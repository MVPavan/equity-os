# Workstream: data-foundation

**What.** Moves Equity-OS from per-company SQLite facts and loose report files onto one shared
PostgreSQL store. It adds a versioned canonical field dictionary and source mappings, a
cross-source comparator with two checks (extraction and independent corroboration) and a review
queue, and migrates the legacy fact store. It then adds the report ledger and long-term memory,
generated human views, the coverage model (universe registry → screens → watchlist), and a
retention policy with replay after deletion.

**Specs (both approved; the ledger spec amends the data spec's retention and replay clauses):**

- [Canonical financial data and cross-source comparison](../../specs/2026-10-11-canonical-financial-data-and-cross-source-comparison.md) (the "data spec"): Stages 1–4
- [Report ledger, memory and data lifecycle](../../specs/2026-10-12-report-ledger-memory-and-data-lifecycle.md) (the "ledger spec"): Stages 1–5

**Core definition.** [`core.md`](core.md): this workstream is the backend core; what it is, its goal,
and how to verify the core is complete. Whole-backend work and the pilot that decides project
completion: [`docs/backend-roadmap.md`](../../backend-roadmap.md).

**Plan.** [`roadmap.md`](roadmap.md) holds the progress, the estimate and the completion check.
It has ten phases: D1a, D1b and D2–D9. Each one is a spec
stage, ordered by real dependency, except data Stage 1, which is split into a tracer (D1a) and its
completion (D1b). Phase plans are written just-in-time into `plans/<phase-id>.md` when execution
reaches the phase. `tracking/` is generated by the bd render script and never hand-edited.

**Tracking (bd).**

- Label `ws-data-foundation` on every epic (the key that execution filters on).
- One epic per phase, titled `[<phase-id>] <phase name>`, e.g. `[D1a] Canonical comparison tracer`.
  `--spec-id` is the data spec for D1a, D1b, D2, D6 and D8 and the ledger spec for D3, D4, D5, D7
  and D9; `--design` is this roadmap.
- One flat stage child per row of a phase's deliverables table. The stage's acceptance is that
  row's Verify cell.
- Only real dependency edges: the roadmap's phase → phase table for epics and its complete
  stage → stage table for stages, seeded exactly as listed.

**Approvals.** Approval is the reviewer's `APPROVE` verdict under
[`.claude/rules/core/04-agent-stack.md`](../../../.claude/rules/core/04-agent-stack.md), not the
owner's. This applies
to the roadmap structure, each deep phase's plan, the frozen acceptance manifests and the register
amendments. The data spec's owner-reserved §6 steps (import-manifest confirmation,
unresolved-originals preflight, Stage 2 cutover) are also reviewer-approved under the owner's
2026-10-12 autonomy directive; the orchestrator executes them and informs the owner.

**Execution.** `/phase-execution <phase-id>` runs one phase. `/run-phases` walks the remaining phases.
