## Design decisions

These are authoritative; tasks cite them by number.

### D1 Digests live in SQL

- **One encoding.** Every D1 digest is SHA-256 over the concatenation, in a fixed documented
  order, of `eqos.enc(field::text)`: `'N'` for null, else `'S' || octet_length(utf8) || ':' ||
  value`. Length-prefixed and null-tagged, so separators inside a value, null versus empty and
  multi-byte text cannot collide. Casts are explicit (`to_char`, `::text`; timestamps UTC
  ISO-8601, microseconds, `Z`), never `jsonb::text`. (`contracts.snapshot.canonical_sha256` is not
  reused: its `json.dumps` output, `ensure_ascii` escapes included, cannot be reproduced
  byte-exactly in SQL, and the triggers must compute the digests.)
- `eqos.version_sealed_digest(version_id)`: over the version's content (row, sections, claims with
  citations, import sources) in key order. `SUBMIT` and `IMPORT_SEAL` carry it; the trigger
  recomputes it.
- `eqos.subject_digest(subject_kind, subject_id)` (0013): `version_sealed_digest` for a version;
  for a proposal, the proposal row, its queue item and (if any) its pair outcome; for an
  interpretation, its row and operand rows. Every decision on those subjects carries it as
  `sealed_digest`; the trigger recomputes it.
- Chain digest: over the row fields in a fixed order, then the predecessor digest; computed by the
  trigger, so `recorded_at` is inside it. Python never re-implements a digest except the test-local
  recompute helper.

### D2 Roles, credentials and privileges (R3′)

- **Group roles** `eqos_panel`, `eqos_owner`: NOLOGIN, created if missing by
  `ensure_group_roles(admin)` (called by `bootstrap_roles` and by the test harness before
  migrating; never altered). Migrations grant only to group roles.
- **Credential file.** `<secrets_dir>/eqos_panel.login` and `eqos_owner.login`, one line
  `<login>:<password>` (split at the first `:`; the login must match `[a-z_][a-z0-9_]*`). The
  file carries the username, so a randomized test login reaches the CLI with no extra config.
- **Login roles.** Live: `fundamentals db bootstrap` reads each file that exists and creates the
  named login with that password, granted its group; a name that already exists is a no-op when
  it is already a member of that group, else refused (never altered, never granted). A missing
  file skips only that login (logged `pg_role_login_skipped`); operators use
  `eqos_panel_login`/`eqos_owner_login`. Tests: per session the harness creates
  `<test_db_prefix>panel_<hex>` and `<test_db_prefix>owner_<hex>` as admin with
  `secrets.token_urlsafe(32)` passwords (no `:`), grants the groups, writes the two 0600 files into
  a tmp secrets dir for CLI tests, and drops both roles at session end. Nothing skips; a harness
  that cannot create roles fails loudly.
- **Connection.** `PgRole` gains `PANEL` and `OWNER`. `PgSettings.conninfo` and `open_pool` take
  `login: RoleLogin | None`; PANEL and OWNER require it and add `-c role=eqos_panel` /
  `eqos_owner` to `options`, so `current_user` inside the session is the group role; other roles
  refuse a login. `PgSettings` gains no field; `.env` and `.env.example` are unchanged.
- **Secrets.** `pg/role_secrets.py`: `secrets_dir(environ) → Path` (`EQOS_SECRETS_DIR`, default
  `~/.secrets`) and `load_login(role, secrets_dir) → RoleLogin` (login and password from the credential
  file), which refuses a missing file, a non-regular file, a file not owned by the process uid,
  any group/other mode bit, or a malformed line, naming the path only. Only `ledger` commands, `compare queue dispose` and `db bootstrap` call them, at the
  CLI edge; a missing file refuses only those commands.
- **Admin and migrator (bead `eqos-z53`, 2026-10-22).** The same loader reads
  `eqos_admin.login` and `eqos_migrator.login` (`CREDENTIAL_FILES`) into
  `PrivilegedPgSettings`, a `PgSettings` subclass built by `load_privileged`. Only the `db`
  actions and `retention purge`/`licence-end` (their final backup dumps as admin) build it.
  `PgSettings` no longer has `user`, `password` or `migrator_password` and refuses an admin or
  migrator conninfo, so a runtime command holds neither even if `.env` still lists them.
  `EQOS_PG_USER` stays in `.env` for compose only.
- **Decider role.** The decision trigger maps `current_user` `eqos_runtime`/`eqos_panel`/
  `eqos_owner` to `RUNTIME`/`PANEL`/`OWNER`; any other user is refused.
- **Privilege matrix** (least privilege per command; INSERT includes USAGE on that table's
  identity sequence; nobody gets UPDATE, DELETE or TRUNCATE):

  | Object | runtime (draft, submit, check, propose) | panel (import, review) | owner (decide, dispose) |
  |---|---|---|---|
  | `USAGE` schema `eqos`; `EXECUTE` `store_now()`, `lock_queue()`, `lock_subject()`, the D1 digest functions, `proposal_amount()`, `version_superseded()` | yes (existing grants kept) | yes | yes |
  | `SELECT` on every `eqos` table (claim check, overlay and gate reads) | yes | yes | yes |
  | `INSERT` `reports`, `report_versions`, `report_sections`, `numeric_claims`, `import_sources`, `validations`, `validation_claim_states` | yes | yes | — |
  | `INSERT` `qa_records`, `legacy_acquisitions` | — | yes | — |
  | `INSERT` `decisions` (kinds limited by D3) | yes | yes | yes |
  | `INSERT` `panel_reviews` (0013) | — | yes | — |
  | `INSERT` `disposition_proposals` (0013) | yes | — | — |
  | `INSERT` `queue_dispositions` | grant kept from 0006; refused by trigger | yes (D11-limited) | yes |

  Verified through the real login pools: a privilege probe per row, a successful import (panel),
  a successful proposal acceptance (panel) and a direct disposition (owner).

### D3 Subjects, kinds and legal transitions

One `decisions` table carries a `(subject_kind, subject_id)` chain. The trigger enforces the
legal predecessor (chain head) for each kind and role, and a Python enum map mirrors it:

| Subject | Head before | Kind | Role |
|---|---|---|---|
| `REPORT_VERSION` | none, version has no import sources | `SUBMIT` | runtime |
| `REPORT_VERSION` | none, version has import sources and was created in this transaction | `IMPORT_SEAL` | panel |
| `REPORT_VERSION` | `IMPORT_SEAL` in this transaction | `IMPORTED_APPROVAL` | panel |
| `REPORT_VERSION` | `SUBMIT` | `APPROVE`, `REQUEST_CHANGES`, `REJECT` | panel (D10) or owner |
| `REPORT_VERSION` | `APPROVE` or `IMPORTED_APPROVAL`; or `IMPORT_SEAL` when `version_superseded()` | `WITHDRAW` | owner |
| `DISPOSITION_PROPOSAL` (0013) | none | `ACCEPT`, `REJECT` | panel (D10) or owner |
| `INTERPRETATION` (0013) | none | `ACCEPT`, `REJECT` | owner only (D10) |
| `REPORT` | any | `SET_POLICY` (D12) | owner |

Everything else is refused: approve before submit, a repeated `SUBMIT`, `SUBMIT` on an imported
version, any decision after `REQUEST_CHANGES`, `REJECT` or `WITHDRAW`, a second decision on a
proposal or interpretation. `WITHDRAW` is owner-only (the spec names no panel withdrawal), and so is every decision on an
interpretation: the trigger refuses a panel decision on an `INTERPRETATION` subject.
`version_superseded(id)` is true when a descendant's chain holds `APPROVE`; supersession of a
withdrawn version still shows `WITHDRAWN`.

### D4 Seal, subject lock and approval binding

- **Subject lock.** `eqos.lock_subject(kind, id)` takes a transaction-level advisory lock. Triggers
  call it before their `store_now()` on every content insert, validation insert and decision
  insert for that subject. Lock order: `lock_queue()` (if the transaction takes it), then the
  subject lock, then the first `store_now()`. Every decision on a `DISPOSITION_PROPOSAL` (panel or
  owner, `ACCEPT` or `REJECT`) takes `lock_queue()`: the decision trigger calls it (re-entrant)
  before the subject lock, so a caller that read `store_now()` first is refused. One queue lock
  therefore serializes all decisions across the proposals of one item (D11 owner precedence).
- **Version chain (0012).** `report_versions` has `UNIQUE (id, report_id)`, a composite foreign
  key `(predecessor_id, report_id) → (id, report_id)` (a predecessor is an earlier version of the
  same report), `CHECK (predecessor_id IS NULL OR predecessor_id < id)` (ids are `GENERATED ALWAYS
  AS IDENTITY`, so a predecessor is strictly earlier: self-links and cycles are impossible),
  `UNIQUE (predecessor_id)` and a partial unique index on `report_id WHERE predecessor_id IS NULL`
  (one root). Each report's versions are thus one linear chain, whether
  created by import or by drafting, so at most one can be the newest `APPROVED`.
- **Seal.** A content insert after `SUBMIT` or `IMPORT_SEAL` is refused; a decision naming a stale
  head or a wrong sealed digest is refused. An interpretation's decided payload includes its
  operands, which D1a can still append (`interpretation_operands` takes new ordinals), so 0013 adds
  a trigger on `interpretation_operands` inserts: it takes the `INTERPRETATION` subject lock and
  refuses once an owner decision on that interpretation exists; an insert before the decision
  changes `subject_digest`, so the decision's digest check refuses a stale one. `content_hash` (P2) is computed in Python by
  `narrative()` and stored on the version row; `submit` recomputes it and refuses a mismatch.
- **Binding (trigger-authoritative).** Under the subject lock, an `APPROVE` must name the
  version's latest validation (highest id), which is `AS_KNOWN`, has `sealed_digest` equal to the
  decision's and to `version_sealed_digest`, has no version-level state, and has exactly one
  state per claim, each `MATCH` or `MATCH_UNTRUSTED`. A validation committed between a decider's
  read and its insert therefore makes the insert fail. `decide()` and `review()` pre-check the
  same rule for a readable error.

### D5 Placeholders and styles

- Claim placeholder `{{c:<claim key>|<style>}}`; prose markers `{{e:<class>}}` and
  `{{s:<capture id>|<anchor>}}` (anchor `p<page>.b<block>.<start>:<end>`, a PDF span).
- Style: comma-separated tokens from a closed enum: one of `group-none`, `group-indian`,
  `group-intl`; `plus`; `unit`; `qual`; one of `range-dash`, `range-comma`; `trim`; `quote`
  (`SOURCE_QUOTE` only). Empty = `group-none`, no sign, unit and qualifier omitted, `range-dash`,
  no trim. A range whose bounds are equal renders one value (as the generator's
  `_format_bounds`); the unit attaches once, after the range. `trim` drops trailing fractional zeros (and a bare point) after rounding; it is needed
  because the legacy generator prints the same value as `256.70` in a trace and `256.7` in a table
  (D7 evidence; gap G8).
- Precision and rounding mode live on the claim. Indian grouping is 2-2-3; the sign shows only for
  a value above zero after rounding; `%` attaches without a space, other units take one space.
  An unknown token makes the section invalid.

### D6 Import claim keys

Per earnings-update version, claims come from the JSON twin; aliases are twin fields that map to
an existing claim (equal values required, else that version's import fails):

| Key | Value field | Citation | Aliases |
|---|---|---|---|
| `fact.<role>` | `facts[*].value` | `FIGURE` | `comparatives[*].current_value` (same concept) |
| `cmp.<role>.<qoq\|yoy>.prior` | `prior_value` | `FIGURE` | — |
| `cmp.<role>.<qoq\|yoy>.abs` | `absolute_change` | `CALCULATION` | — |
| `cmp.<role>.<qoq\|yoy>.pct` | `percent_change`, precision 1, `ROUND_HALF_EVEN` (generator `_PERCENT_QUANTUM` under a default `Context`) | `CALCULATION` | — |
| `calc.<n>` | `calculations[n-1].result` | `CALCULATION` | — |
| `ledger.<metric>.<horizon>.<scope>` | `ledger.entries[*]` bounds, unit, constant-currency, horizon, scope; quote and anchor = `latest` | `SOURCE_QUOTE` | `guidance[g]` whose `quote`, `source`, bounds, unit, constant-currency and horizon equal an entry's `latest` with `latest.issuer_quarter` = this quarter (exactly one match; `metric_label` stored on the claim's guidance contract); management-ledger `history` revisions for this quarter; the version twin's `entries[*].history[*]` items, matched against the `(quarter, key)` claim of their quarter's mapped version |

- No `guide.*` key exists: when the twin has a `ledger`, the generator renders only
  `ledger.entries` and never `guidance` (`output/earnings_update.py` lines 429–468), so a separate
  guidance claim would have no display.
- Qualifiers come from the claim's own quote by `quote_qualifiers` (Task 2), a closed lexicon (`plus` for "-plus"/"plus",
  `about` for "about", whole words); the manifest freezes them independently.
- Q0 adds `falsifier.<falsifier_id>`: a self-cited `POLICY` claim on
  `falsifiers[i].predicate.threshold` (five: F1–F5). Other numerals in Q0 prose stay literal.
- `cross_check` and `cross_foot` counts and the `approval_record` section become QA records.
- Resolution: a `FIGURE` resolves to a fact `(origin, origin_id)` by measurement key and source
  file SHA-256; imported `CALCULATION`s have no stored trace, so they are `UNRESOLVED` (the spec's
  open question "Legacy-fact claims"); a `SOURCE_QUOTE` resolves to a `capture_refs` row by file
  SHA-256; otherwise `UNRESOLVED`. All resolution also passes D9's authority checks.

### D7 Lossless mapping by explicit slots

- **Sections:** the Markdown splits at lines beginning `## `; section 0 (`preamble`) holds title
  and lead; the trailing `---`/`### Sources` block stays in the last section. Rendered sections
  concatenated equal the file bytes, so an earnings update's content hash is its `.md` SHA-256.
- **Slots:** the mapper rebuilds each bound line from the twin with the generator's line shapes
  (`output/earnings_update.py`: facts row, changes row, trace line, ledger line, calculation
  line) and assigns every value slot an explicit `(claim key, style)`:
  - facts row: `fact.<role>` `group-intl,trim` (crore) or default precision 2 (EPS);
  - changes row: current `fact.<role>` and `prior` `group-intl,trim`; `abs` `plus,group-intl,trim`;
    `pct` `plus,unit`;
  - trace line: current and prior values with an empty style (the twin's raw lexemes);
  - ledger line: the bold bounds `range-dash,unit,trim` at precision = the most fractional digits
    of the two twin bound lexemes (qualifier omitted); the claim's own quote with
    `quote` in the slot that shows `latest.quote` (the "first quoted" slot for `NEW`, the
    "restated" slot for `MODIFIED`/`REAFFIRMED`, none for `CARRIED`);
  - calculation line: `calc.<n>` result, empty style.

  Every other byte of a bound line is literal and must equal its twin text field (labels,
  `first.quote` when it is not the claim's quote, `trace`, period labels, the `(was …)` bounds of
  `history[-1]`, footnote markers; each twin `source` object maps to its `[^n]:` line in the
  Sources block, rebuilt with the generator's `anchor_label`). Imports are exempt from the numeral scan (ledger §1 "at
  `SUBMIT`, imports exempt"), so literal numerals are allowed. A line whose rebuild differs from
  its bytes, or a twin field with no slot, alias or literal, fails that version's import. No
  "every equal numeral" matching exists, so shared displays cannot collide.

### D8 Legacy first-seen time

The D1a intake stamps `capture_refs.registered_at` and `first_seen_at` from the store clock
(`stage_retained_member()`, `capture_intake.py:247`), and `RetainedCaptureBinding` keeps no
acquisition time, so the D2 rig's captures cannot yield the September timestamps. Fix, with no
change to D1/D2 code, migrations or approved manifests:

- **Persisted:** `eqos.legacy_acquisitions` (0012): `blob_sha256`, `retrieved_at`,
  `manifest_sha256`, `entry_sha256`, `recorded_at` (trigger); `UNIQUE (manifest_sha256,
  entry_sha256)`; append-only; panel INSERT only.
- **Hash-bound:** `store.insert_acquisitions(cursor, manifest_bytes, *, expected_sha256)` refuses
  bytes whose SHA-256 differs from the pin in `config/ledger_import.yaml`
  (`c47866ce…a1b`, the same file `stage1_manifest.yaml` pins as `A-MAN`). Each manifest entry

### D9 Citation authority and location markers

`resolve_citation` returns `None` (row 1, `UNRESOLVED`) unless the cited record has authority:

- `FIGURE`, `CALCULATION`: first-party only, judged by `SourceCatalog.describe(source_id)` of the
  capture behind the fact, the interpretation, or every trace operand. A `FIGURE` naming an
  interpretation and run resolves only through a `result_source_values` row with `source_state =
  'VALUE'` and that `interpretation_id`, whose result belongs to the named run and has the claim's
  `key_digest`; the cited value is that row's value and the source identity its interpretation's
  capture. Membership in `run_inputs` is not enough (it also lists `SURFACED` and
  `NOT_SELECTED` interpretations).
- `SOURCE_QUOTE`: the capture's source is not `VENDOR`.
- `COMPARISON`: the result belongs to the named run and key, and the pair is the named source pair.
- `POLICY`: an owner `SET_POLICY` decision on a report of the same entity (D12), or for an import
  only, its own version's record.

`{{s:<capture id>|<anchor>}}` resolves when the capture exists with a non-vendor source and
`verify_quote_anchor(…, "", source_document(pdf))` anchors the span in the capture bytes from
`SnapshotStore`, the same path as quote resolution, and the resolved text is non-empty after
stripping whitespace (an empty expected quote alone would let a `0:0` span pass). `submit` and `validate` both resolve every
marker with the `catalog` and `snapshots` passed in from the composition root; a failing one makes the paragraph `UNCITED_PROSE`.

### D10 Panel reviews

- **Row** `eqos.panel_reviews` (0013): `subject_kind`, `subject_id`, `sealed_digest`, provider,
  model, effort, brief version, `verdict` (`APPROVE`, `REQUEST_CHANGES`, `REJECT`), rationale,
  `rationale_sha256` (trigger-computed), `created_xid` (trigger, `txid_current()`), `recorded_at`.
- **Decision rule** (trigger, for every panel decision but `IMPORT_SEAL`/`IMPORTED_APPROVAL`):
  `panel_review_id` is non-null and unique across decisions; the review's subject equals the
  decision's; its `sealed_digest` equals the decision's; its `created_xid` is the current
  transaction; its verdict maps to the decision kind (`APPROVE→APPROVE`,
  `REQUEST_CHANGES→REQUEST_CHANGES`, `REJECT→REJECT` for versions; `APPROVE→ACCEPT`,
  `REJECT→REJECT` for proposals, where `REQUEST_CHANGES` is refused). Owner
  decisions carry no review. **The panel makes no decision on an interpretation**: the trigger
  refuses a `PANEL` decision on an `INTERPRETATION` subject, and `review()` refuses the subject
  kind before any reviewer call. Why: nothing in D3 consumes interpretation approvals (F2), and
  `revision_cause` is descriptive metadata, not deterministic provenance, so panel acceptance would
  need a provenance/replay check that belongs with F2. The panel is refused on a subject whose chain holds an owner
  decision (proposals: D11).
- **Per subject** (`review()` runs the gates, calls the reviewer only if all pass, then re-runs the
  gates in the deciding transaction under its locks and inserts the review and decision there):

  | Subject | Reviewed payload (`subject_text`) | Digest | Deterministic gates |
  |---|---|---|---|
  | `REPORT_VERSION` | `narrative()` bytes of the sealed version | `version_sealed_digest` | head is `SUBMIT`; D4 binding rule on the latest validation; no owner decision |
  | `DISPOSITION_PROPOSAL` | canonical JSON of proposal, queue item and bound pair outcome | `subject_digest` | chain empty; item open in the overlay; D11 owner precedence; amount source valid (D11) |

  Overlay reads: the preliminary gate uses `overlay_boundary()` and `read_overlay()` (own
  transactions). The final gate must not call `overlay_boundary()`, which opens a second
  transaction that would wait on the deciding transaction's own queue lock; instead the deciding
  transaction takes `lock_queue()`, then the subject lock, then reads `eqos.store_now()` as its
  boundary and calls `overlay_at(cursor, run_id=…, as_of=<that time>)`. A change between the two
  gate runs (a new validation, a disposition, an owner decision) refuses with no
  decision row (`ReviewStaleError`).
- `ReviewOutput` is `(verdict, rationale)` with `extra="forbid"`: a reviewer cannot return an
  amount.

### D11 Queue gating, proposals and amounts

- **0012:** a `queue_dispositions` insert by `eqos_runtime` is refused. `compare queue dispose`
  runs as owner (the spec's "owner dispositions remain and outrank"); it is the only path for a
  manual amount.
- **0013 `disposition_proposals`** (runtime inserts via `compare queue propose`): item, kind,
  reason, evidence ref, `pair_outcome_id`; `pair_outcome_id` is set exactly for
  `ACCEPTED_AS_DEFINITION`, and the trigger requires the bound `pair_outcomes` row to match the
  item on run (`results.run_id`), measurement key (`results.key_digest`), ordered source pair
  (`left_value_id`, `right_value_id`), `pair_kind` and `outcome`, and to have a non-null,
  non-zero `difference`. The source pair and kind are checked against the item's `pair_identity`
  (`routing.pair_identity`: digest of `pair_kind`, `left`, `right`); a result holds several pairs
  (`PairRecord`), so run and key alone would let a proposal bind a sibling pair. No amount column.
  **Mechanism (orchestrator ruling, r2):** SQL cannot recompute that canonical-JSON digest, so
  0013 adds a nullable `pair_outcomes.pair_identity`, written by the comparison writer from
  `routing.pair_identity` in the same insert as the outcome (the same code that routes the queue
  item, so both sides use one function). The trigger requires it non-null and equal to
  `queue_items.pair_identity`. Outcomes stored before 0013 have it null, so the panel cannot bind
  them; the owner's `compare queue dispose` still can. The frozen Stage 1/2 oracles do not read
  this column; Task 4 confirms both e2e tests stay green.
- **Amount:** `eqos.proposal_amount(proposal_id)` = `abs(pair_outcomes.difference)` or null (the
  stored deterministic difference; `definition_records.explained_amount` is positive).
  `decisions` has no amount column.
- **Accept:** an `ACCEPT` on a proposal, by panel or owner, inserts its disposition in the same
  transaction (`lock_queue()` first), with `evidence_ref = decision:<id>` and
  `explained_amount = proposal_amount()`. A deferred constraint trigger refuses commit of an
  `ACCEPT` without exactly one such disposition.
- **Disposition trigger (0013):** an `evidence_ref` of form `decision:<id>` must name an `ACCEPT`
  decision, created in this transaction, on a `DISPOSITION_PROPOSAL` (the proposal itself is
  normally committed earlier, by the runtime) whose item, kind and reason equal the
  row's and whose `proposal_amount()` equals `explained_amount`; a unique partial index allows one
  disposition per decision. Panel inserts must take this form; owner inserts may also be direct.
- **Owner precedence:** a panel decision on a proposal is refused when the item already has any
  disposition, or any proposal of the same item has an owner decision. The trigger checks this
  after taking `lock_queue()` (D4), which every proposal decision holds, so an owner decision on
  proposal A and a panel decision on proposal B of one item cannot both pass unseen.

### D12 Owner policy values

A new report's `POLICY` value comes from an owner decision `SET_POLICY` on the `REPORT` subject,
with `policy_key`, `policy_value numeric` and `policy_unit` (non-null exactly for `SET_POLICY`)
and the verbatim ruling: `fundamentals ledger decide REPORT <report_id> SET_POLICY --key <k>
--value <v> --unit <u>`. A draft claim cites it by decision id; row 5 compares the value, row 2
(`AS_KNOWN`) its `recorded_at`. Self-citation stays import-only (gap G9).
