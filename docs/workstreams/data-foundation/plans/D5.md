## Design decisions

### D1 What "the views" are (0021)

The spec's dashboard "reads through a read-only role (SELECT on views)". A dashboard needs the
same two things the Markdown export shows, as rows: report status and promoted memory. D5 creates
exactly two SQL views, both deriving status at read time from the decision log:

- `eqos.report_status_view`: one row per report version: `version_id`, `predecessor_id`,
  `stock` (`reporting_entities.entity_key`), `period`, `report_kind`, `knowledge_cutoff`,
  `content_hash`, `status` (head `REPORT_VERSION` decision mapped as `lifecycle._HEAD_STATUS`,
  no decision = `DRAFT`; `APPROVED`/`HISTORICAL` with an `APPROVE` or `IMPORTED_APPROVAL` on any
  descendant = `SUPERSEDED`, as `lifecycle._STATUS`), `latest_validation_id`,
  `latest_validation_mode`, `untrusted_claims` (count of the latest validation's claim states
  that are not `MATCH`).
- `eqos.promoted_memory_view`: one row per item whose derived status is `PROMOTED` (head decision
  `PROMOTE` and no promoted successor, as `retrieval._ITEMS`): `item_id`, `stock` (null for
  cross-stock kinds), `kind`, `statement`, `epistemic_class`, `valid_from`, `valid_to`,
  `recorded_at`. No revalidation flag in the view (ruling V5); the Markdown export shows it.

No view over raw tables, decisions, claims or supports: the notes carry that detail, and no
acceptance needs it as rows. The SQL status mapping duplicates the Python one by necessity (a
SELECT-only role cannot call Python); drift is caught by Task 2's fixture matrix, which compares
complete view membership and rows with `lifecycle.version_status` / `retrieval.retrieve` for
every report head mapping and every memory retirement path, and by the e2e. Both views read the
tables inline (as `lifecycle._STATUS` and `retrieval._ITEMS` do); no function is created or
called.

### D2 Read-only role and provisioning

- A third NOLOGIN group role `eqos_reader`, added as `PgRole.READER` to `GROUP_ROLES` in
  `src/fundamentals/pg/settings.py`. This reuses the existing provisioning with no new code path:
  `ensure_group_roles` creates it, `bootstrap_roles` grants it `CONNECT`, `db bootstrap`'s
  `_create_logins` creates a member login only if `<secrets>/eqos_reader.login` exists (skips
  otherwise), and the test harness's `_session_logins` creates a randomized reader login and
  credential file per session. No password or secret appears in any migration.
- 0021 (run by the migrator, which owns the views): `GRANT USAGE ON SCHEMA eqos TO eqos_reader;
  GRANT SELECT ON eqos.report_status_view, eqos.promoted_memory_view TO eqos_reader;` and nothing
  else. Views are not `security_invoker`, so the reader needs no base-table privilege.
- Writes are refused: the reader holds no INSERT, UPDATE or DELETE on anything. A write to a
  non-updatable view (aggregates/joins) fails in the rewriter with SQLSTATE `55000` before the
  privilege check (`42501`), so view-write tests accept either code and separately assert
  `has_table_privilege` is false for each write privilege on each view. Base-table writes raise
  `InsufficientPrivilege`. No write triggers.

### D3 Exports (`ledger export` extension)

- `src/fundamentals/ledger/export.py` gains `status_note(cursor, version_id) -> str`: Markdown
  with the version's identity (stock, period, kind, chain position), derived status
  (`version_status`), its decisions in sequence order (kind, decider role, recorded time),
  latest validation (`store.latest_validation`: id, mode, creator, version-level states), untrusted
  claims (every claim state in that validation that is not `MATCH`, by key with its state; spec
  line 235 lists `MATCH_UNTRUSTED` there, and memory treats every non-`MATCH` claim as
  untrusted), and revalidation flags (promoted items of the stock with `needs_revalidation`
  whose supports name this version, from `retrieval.retrieve(query="", statuses={PROMOTED})`
  and `SupportRef.version_id`). No narrative text enters the note.
- `src/fundamentals/memory/export.py` (new, small): `format_memory(items: Sequence[RetrievedItem])
  -> str`: one Markdown section per item (kind, statement verbatim, epistemic class, valid range,
  recorded time, revalidation flag, supports as `period kind claim_key` from `SupportRef`, or
  target kind and id), in id order. Engine-neutral: it formats the results of
  `MemoryStore.retrieve(query="", stock=…, kinds=None, statuses={PROMOTED}, cutoff=None)`, which
  every arm implements, so export (spec §2, D4 C2) needs no Protocol method and no database code.
- CLI: `ledger export --stock <symbol> --out <dir> [--status-notes] [--memory]` writes, under
  `<dir>/<symbol>/`, `<period>-<kind>-v<n>.md` (narrative bytes, `n` = position in the report's
  version chain, root 1) for every version of the stock. Stock and period are stored free text, so
  each must be a safe single filename component (`[A-Za-z0-9._-]+`, not `.` or `..`) or the export
  is refused before any write, and every resolved path must lie under `<dir>` (critical review F4); with `--status-notes` also
  `<period>-<kind>-v<n>.status.md`; with `--memory` also `memory.md`. Runs as the runtime role
  in one `REPEATABLE READ, READ ONLY` transaction (as `PgMemoryStore._snapshot`) for narratives and
  status notes; `memory.md` is `format_memory(PgMemoryStore(pool).retrieve(...))`, one retrieve
  in its own snapshot. **Snapshot consequence:** `memory.md` and the status notes may come from
  two snapshots, so a memory decision committed between them can make a note's flags disagree
  with `memory.md`. The spec (§3, Stage 3) asks for status notes and promoted memory per stock,
  not one snapshot across both, so this is accepted; each file is internally consistent and
  re-export regenerates both. The existing
  `ledger export <version id> [--out PATH]` form is unchanged; the two forms are mutually
  exclusive.

## Open questions and assumptions

- **Q1 Revalidation flags in a report's status note.** Assumed: promoted items of the stock that
  derive `NEEDS_REVALIDATION` and cite this version directly or through one of its claims. The
  spec lists the field without defining its scope. In the Apar end state the list is empty;
  Task 1's fixture exercises a non-empty one.
- **Q2 Ruled (V5):** no revalidation flag in the SQL view; `memory_item_supported` unchanged.
- **Q3 "Untrusted claims" = every non-`MATCH` state** (superset of `MATCH_UNTRUSTED`). If only
  `MATCH_UNTRUSTED` is meant, the Apar imported versions list nothing, which hides that their
  claims are `UNRESOLVED`/`POST_CUTOFF`.
- **Q4 Export file naming** by `<period>-<kind>-v<n>` (chain position), because version ids vary
  per database and there is no version-number column. The narrative bytes are unaffected.
- **A1** The test harness bootstraps group roles before migrating (`create_test_database` →
  `bootstrap_roles`), so 0021's grants find `eqos_reader`; a database bootstrapped before D5 needs
  `fundamentals db bootstrap` re-run before migrating to 0021 (the GRANT fails loudly otherwise).
  To verify in Task 2, not guessed.
- **A2** The export runs as the runtime role, not the reader: the reader can see only the views,
  and the narrative needs sections and claims.
- **A3** The Stage 2 e2e's state build can be extracted without changing its assertions; if it
  cannot be cleanly separated, Task 5 instead calls the same steps through a shared helper in
  `ledger_cited_support.py` or `memory_support.py`, again without assertion changes.
