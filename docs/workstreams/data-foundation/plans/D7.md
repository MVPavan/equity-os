# D7 Coverage Model Implementation Plan

Status: draft — pending Sol review

**Origin:** Phase D7 row of [`roadmap.md`](../roadmap.md) (stages D7.1–D7.6, exit, edges D7 → D6,
D7 → D3, D7 → D6b); stages `eqos-3oq.1`–`.6` (acceptance read from bd 2026-10-17). Specs:
[ledger spec](../../../specs/2026-10-12-report-ledger-memory-and-data-lifecycle.md) O6–O8, O10,
amendment 1, §4, Success Criteria Stage 4; [data spec](../../../specs/2026-10-11-canonical-financial-data-and-cross-source-comparison.md)
§8. Conventions from [D3](D3.md), [D5](D5.md), [D6](D6.md), [extractor v2](extractor-v2.md).
**Goal:** an owner-only registry, screen run, capture batch and watchlist, where a batch onboards
(D6) and compares exactly the chosen members, and the runtime role cannot draft a report for a stock
that is not on the watchlist.
**Out of scope:** live acquisition inside a batch (R4, follow-up bead); retiring the legacy
`screener-screen` command (R5, follow-up bead); NSE `BE` series (`eqos-z48`); the suspended
instrument list; retention classes and catalog basis (D9.2); drafting agents (`eqos-4j2.8`);
system-chosen coverage or scheduling of any kind.
**Constraints:**
- Migrations forward-only; `0001`–`0023` exist and are immutable; D7 adds `0024`–`0026`.
- Registry rows never write the identity layers (`0022`); capture still needs §8 verification.
- The system never requests a Screener screen URL; a screen's only input is an owner-exported CSV.
- Nothing is scheduled; every command runs to completion on an owner invocation.
- `ADD`/`REMOVE` are owner-role decisions with a verbatim ruling on the D3 chain (O10).
- Models never compute numbers: manifest values come from a throwaway `scratchpad/` aid that never
  imports `fundamentals`.
- Held-out discipline still binds: no committed fixture holds a non-development company; the full
  instrument list is read from gitignored `data/` only.
- `discovery.py` is at its 800-line cap and is not edited; `test_frozen_manifests.py` (783) grows
  ≤ 5 lines; `mypy --strict`, ruff, frozen Pydantic, enums, structlog, no loose strings.
- Owner code-size rule: each module traces to a stage acceptance below.

## Rulings (proposed; Sol approves with the plan)

- **R1 Paths.** Roadmap `0008_coverage.sql` → `0024_coverage_registry.sql` (D7.1),
  `0025_coverage_batches.sql` (D7.2), `0026_watchlist.sql` (D7.3). D7.4's record is a **new** file
  `docs/blueprint/amendments/2026-10-17-coverage-initiation.md`, not an edit of
  `2026-10-12-report-ledger.md`. `coverage/watchlist.py` is not created (nothing consumes it: the
  chain reuses `ledger decide`); D7.3 modifies `contracts/ledger.py` and `ledger/lifecycle.py`
  instead. The orchestrator edits the roadmap row when recording this plan.
- **R2 Owner role writes coverage.** Registry, screen, screen-run and batch tables are INSERT-granted
  to `eqos_owner` only (SELECT to all three roles); `run_by` defaults to `current_user`. The
  runtime role (drafting agents) therefore cannot launch a batch or pick coverage (amendment 1).
  The `coverage` CLI opens the owner login as `ledger decide` does; onboarding inside a batch keeps
  its own runtime pool.
- **R3 Verified identity = admitted onboarding.** `ADD` needs the entity's latest onboarding record
  to be `ONBOARDED` or `PARTIAL` and a batch-member row for the entity with a stored run. `PARTIAL`
  must count: R-PDF makes it the best outcome any company reaches today.
- **R4 Batch inputs are retained generations (replay).** `coverage batch --raw-root <dir>` expects
  `<dir>/<SYMBOL>/gen-<n>/` (the live-smoke layout) and replays each member through D6. Live
  acquisition needs an acquisition authority other than the held-out freeze descriptor; that is a
  change to D6's `_frozen` and is filed as a follow-up bead, not built here.
- **R5 `?q=` rule.** The coverage path makes no network request at all (socket guard in tests). The
  legacy `screener-screen` command contradicts §4 ("never requests") but is not on the coverage
  path; a follow-up bead retires it (touches `eqos-kx4.5`).
- **R6 Drafting gate.** "Drafting" = a report version inserted by the runtime role. A trigger on
  `eqos.report_versions` refuses it unless the report's entity is watchlisted and either the report
  is a `BOOTSTRAP_THESIS` or the entity has an earlier `BOOTSTRAP_THESIS` report. Imports (panel
  role) are historical records, not drafting, and pass. Gating at the version (not the report or
  `SUBMIT`) also refuses a new version of an old report after `REMOVE`.
- **R7 Batch members.** Batch = **ETERNAL, POLYCAB, TITAN**; the other two screen members =
  **THERMAX, CGPOWER**. All five are `PARTIAL` in the v2 smoke with generations as of 2026-10-17
  (ETERNAL, POLYCAB, TITAN, CGPOWER `gen-1`; THERMAX `gen-3`), all formerly phrase-free filers, so
  the batch exercises the D7 → D6b edge. ETERNAL is chosen because its ISIN carries a real former
  NSE symbol (ZOMATO) for the registry candidate-event step. Not chosen: APARINDS (pre-seeded in
  ledger tests; re-onboarding an existing issuer is `eqos-g2q` territory), SONACOMS (owner dropped
  it from the comparison set 2026-10-14), NETWEB/HFCL/MTARTECH (not admitted).

## Tasks

### Task 1: Universe registry and idempotent refresh

Goal: a retained instrument list yields the expected rows; reloading it changes nothing; an ISIN
seen under a new symbol in the same segment records a candidate event and leaves the identity
layers unchanged.
Stage: eqos-3oq.1
Files: Create `0024_coverage_registry.sql`, `coverage/__init__.py`, `coverage/registry.py`,
`api/coverage_cli.py` (`registry` action), `tests/fundamentals/coverage_support.py`; Modify
`api/cli_parser.py`/`cli.py`; Test `test_coverage_registry.py` (`pg`, `retained`).
Interfaces:
- Consumes: `read_instrument_catalog`, `UpstoxInstrument`; `discovery.store_captures` with the
  registered `UPSTOX_INSTRUMENTS` surface (no new catalog entry); `identity_layers.latest_slice`.
- Produces: `load_registry(pool, instruments: Path, snapshots: SnapshotStore) -> RegistryLoad`
  (`load_id: int`, `created: bool`, `new_listings: int`, `candidate_events: int`); tables above;
  `eqos.registry_view`; CLI `fundamentals coverage registry --instruments <json.gz> --snapshot-root <dir>`.
Approach: one row per instrument key (`NSE_EQ` rows carry the NSE symbol, `BSE_EQ` rows the scrip
code as `exchange_token`). A load whose content SHA-256 is already recorded returns
`created=False` and writes nothing. Otherwise one load row, the capture, new listings, one
sighting per listing; for each `(segment, ISIN)` whose symbol differs from its listing in the
previous load, one candidate event. Status and last-seen are derived in the view.
Verification: `uv run pytest tests/fundamentals/test_coverage_registry.py` — load of the
2026-09-04 list matches the aid's row count and dev spot rows; reload returns `created=False` with
table counts unchanged; a re-marked copy (ETERNAL's `NSE_EQ` symbol → `ZOMATO`, labelled
SYNTHETIC) loaded after the real list yields exactly one candidate event while `identity_events`,
`identifier_relationships` and `latest_slice` are unchanged; the runtime role's INSERT is refused.
Dependencies: None.
Risks: decoded list is ~55 MB; load once per test module. The re-marked list is built in
`tmp_path`, never committed (it holds the whole market).

### Task 2: Screens, screen runs and capture batches

Goal: a five-member CSV resolves; a batch over three members onboards and compares exactly those
three, the other two have nothing; no network request; nothing scheduled.
Stage: eqos-3oq.2
Files: Create `0025_coverage_batches.sql`, `coverage/screens.py`, `coverage/batch.py`,
`fixtures/coverage/screen_export.csv`; Modify `api/coverage_cli.py`, `api/onboard_cli.py`,
`api/compare_cli.py`, `contracts/source_catalog.py`, `contracts/canonical.py`; Test
`test_coverage_batch.py` (`pg`, `retained`).
Interfaces:
- Consumes: `registry_listings`/`registry_view` (Task 1); D6 replay; `compare_command`.
- Produces: `record_screen_run(pool, screen_text: str, csv: Path, snapshots) -> ScreenRun`
  (`run_id`, `members: tuple[ScreenMember, ...]`, each `listing_id: int | None`);
  `run_batch(pool, screen_run_id: int, symbols: tuple[str, ...], raw_root: Path,
  snapshot_root: Path, config_root: Path) -> int` (batch id); `onboard_cli.onboard(symbol,
  raw_root, snapshot_root, config_root, generation=None) -> Onboarded` (`outcome`, `entity_id`,
  `compare: str | None`, `exit`); `compare_cli.run_compare(args) -> RunRecord`; CLI
  `coverage screen-run --screen <txt> --csv <csv> --snapshot-root` and
  `coverage batch --screen-run <id> --members A,B,C --raw-root --snapshot-root [--config-root]`.
Approach: the screen definition is stored once by text hash; the CSV is stored as a
`SCREEN_EXPORT` capture. A member resolves by NSE code to the latest-load `NSE_EQ` listing, else by
BSE code to the `BSE_EQ` listing; zero or several matches → `UNRESOLVED`. `run_batch` first refuses
any symbol that is not a resolved member with an NSE listing (nothing written), then inserts the
batch and, per member in order, calls `onboard`, runs the printed command through `run_compare`
when admitted, and appends a `batch_members` row. `_onboard` and `_run` become thin printers over
the extracted functions.
Verification: `uv run pytest tests/fundamentals/test_coverage_batch.py` — five members resolve to
their listings; a batch over ETERNAL, POLYCAB, TITAN (pinned generations copied to `tmp_path`)
records three `PARTIAL` members with stored runs; THERMAX and CGPOWER have no onboarding record,
capture, entity or run; an `UNRESOLVED` or non-member symbol is refused before any write;
`socket.socket.connect` patched to raise stays untouched; an import scan of
`fundamentals.coverage` finds no `sched`, `threading`, `asyncio`, `subprocess` or
`ingest.screener_screen`. Then `uv run pytest tests/fundamentals/test_data_stage4_e2e.py
tests/fundamentals/test_onboarding_acquisition.py` stays green (extraction is behaviour-neutral).
Dependencies: Task 1. Preflight (orchestrator, before dispatch): replay the five chosen
generations with `fundamentals onboard` at `HEAD` on a scratch `eqos_test_*` database and confirm
`PARTIAL`; `ad29c3e` landed after the smoke.
Risks: the CSV header is unknown until the owner's export (Q1). Onboarding three companies costs
minutes; one shared module-scoped database.

### Task 3: Watchlist decisions and the drafting gate

Goal: `ADD`/`REMOVE` are owner-only with a verbatim ruling; adding an unverified or uncaptured stock
is refused; a runtime draft for a stock off the watchlist is refused; a new member's first report
must be `BOOTSTRAP_THESIS`.
Stage: eqos-3oq.3
Files: Create `0026_watchlist.sql`; Modify `contracts/ledger.py`, `ledger/lifecycle.py`,
`tests/fundamentals/coverage_support.py`, `ledger_support.py`, `memory_support.py`,
`test_ledger_stage{1,2,3}_e2e.py` (seed only); Test `test_coverage_watchlist.py` (`pg`).
Interfaces:
- Consumes: `onboarding_records` (0022), `batch_members` (Task 2), `append_decision`, `ledger decide`.
- Produces: `SubjectKind.WATCHLIST` (subject id = entity id), `DecisionKind.ADD`/`REMOVE`;
  `eqos.watchlisted(entity bigint) RETURNS boolean` (also D9.2's covered-stock test);
  `eqos.watchlist_digest(entity)` = SHA-256 of the latest admitted onboarding record and latest
  batch member with a run, NULL if either is missing; test helper `watchlist(pools, entity_id)`.
Approach: `TRANSITIONS` gains `ADD` (owner; head `None` or `REMOVE`) and `REMOVE` (owner; head
`ADD`). The trigger mirrors `check_memory_decision`: owner only, stale-head refusal, non-empty
ruling, `sealed_digest = eqos.watchlist_digest(subject)`. A NULL digest makes `store.subject_digest`
raise before insert, so unverified and uncaptured stocks are refused in both layers. The drafting
gate is R6. Characterization first: apply 0026 and run the ledger and memory suites to list what
the gate breaks, then add the seed to the shared fixtures (one bootstrap report in `Ledger`).
Verification: `uv run pytest tests/fundamentals/test_coverage_watchlist.py` — owner `ADD` with
ruling accepted; empty ruling, runtime and panel `ADD`/`REMOVE` refused; entity with no onboarding
record, and onboarded but never batched, refused; `REMOVE` then re-`ADD` legal; runtime draft for a
non-watchlisted entity and after `REMOVE` refused; first `EARNINGS_UPDATE` refused, `BOOTSTRAP_THESIS`
then `EARNINGS_UPDATE` accepted; panel import for a non-watchlisted entity accepted. Then
`uv run pytest tests/fundamentals -k "ledger or memory or views"` green.
Dependencies: Task 2.
Risks: wide blast radius (every runtime draft in D3–D5 tests); mitigated by seeding in shared
fixtures, not per test. Frozen manifests are untouched; only e2e setup changes.
