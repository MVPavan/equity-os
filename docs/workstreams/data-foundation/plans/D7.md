# D7 Coverage Model Implementation Plan

Status: draft — pending Sol review r2

**Origin:** Phase D7 row of [`roadmap.md`](../roadmap.md) (stages D7.1–D7.6, exit, edges D7 → D6,
D7 → D3, D7 → D6b); stages `eqos-3oq.1`–`.6` (acceptance read from bd 2026-10-17). Specs:
[ledger spec](../../../specs/2026-10-12-report-ledger-memory-and-data-lifecycle.md) O6–O8, O10,
amendment 1, §4, Success Criteria Stage 4; [data spec](../../../specs/2026-10-11-canonical-financial-data-and-cross-source-comparison.md)
§8. Conventions from [D3](D3.md), [D5](D5.md), [D6](D6.md), [extractor v2](extractor-v2.md).
**Goal:** an owner-only registry, screen run, capture batch and watchlist, where a completed batch
onboards (D6) and compares exactly the chosen members, and the runtime role cannot draft a report,
or add content to one, for a stock that is not on the watchlist.
**Out of scope:** live acquisition inside a batch (R4, Q2); deleting the legacy screen-acquisition
subsystem (R5, follow-up bead); NSE `BE` series (`eqos-z48`); the suspended instrument list;
retention classes and catalog basis (D9.2); drafting agents (`eqos-4j2.8`); system-chosen coverage
or scheduling of any kind.
**Constraints:**
- Migrations forward-only; `0001`–`0023` immutable; D7 adds `0024`–`0026`.
- Registry rows never write the identity layers (`0022`); capture still needs §8 verification.
- The system never requests a Screener screen URL; a screen's only input is an owner-exported CSV.
- Nothing is scheduled; `ADD`/`REMOVE` are owner decisions with a verbatim ruling (O10).
- Manifest values come from a throwaway `scratchpad/` aid that never imports `fundamentals`.
- Held-out discipline binds: no committed fixture holds a non-development company.
- `discovery.py` (800, cap) not edited; `test_frozen_manifests.py` (783) grows ≤ 5 lines; strict
  mypy, ruff, frozen Pydantic, enums, structlog; each module traces to a stage acceptance.

  retained generation offline and prints, but does not run, the `compare run` command
  (`api/onboard_cli.py:280-365,509-526`). `--acquire` needs the held-out freeze descriptor
  (`_frozen` `:648-678`). Every company is at best `PARTIAL` (D6 R-PDF; exit 4). Both CLI functions
  are composition roots (`onboard_cli.py:308-330`, `compare_cli.py:222-242`).
- **Retained inputs** (gitignored `data/`). Live-smoke generations under
  `data/raw/onboarding-dev/live-smoke/<SYM>/gen-*` (8 `PARTIAL` at `6aca86f`), each with an Upstox
  list (sha `8ae204e5…` 2026-10-16, `c5404139…` 2026-10-17); a third list at
  `data/raw/upstox/instruments/complete/20260904T082313Z-459ec0544e40/` (sha `459ec054…`). Its
  `review.json` count (3,337) is **stale** (obsolete trading-series filter); the current reader keeps
  company equity by segment and ISIN (`ingest/upstox_instruments.py:65-68,404-418`): **7,845 listing
  keys** (3,132 NSE, 4,713 BSE; 5,409 ISINs), frozen by the aid. The key is `SEGMENT|ISIN`
  (`:160-174`), so a symbol change keeps it. `("upstox", "instruments")` is already an `IDENTITY`
  surface (`contracts/source_catalog.py:228-237,266-269`), outside reconciliation.
- **Screens.** `screener-screen` is registered (`api/cli_parser.py:181`) and dispatches to
  `acquire_screen` (`api/screener_cli_dispatch.py:137-138`), which requests `/screen/raw/?query=…`.
- **Decision chain.** `decide` locks its subject (`ledger/lifecycle.py:364-367`);
  `store.insert_decision` supplies no `decider` (`ledger/store.py:195-212`) and `check_panel_review`
  reads it (`0016:177-188`). `BEFORE` triggers fire in name order: the memory trigger sorts before
  `check_panel_review` and sets the decider (`0016:219-221`); `stamp_decision` sorts last.
- **Drafting.** A `reports` row has no content or time (`0012:6-31`). Runtime inserts sections and
  claims independently of versions (`0012:481-491`); `check_version_seal` guards `import_sources`,
  `report_sections`, `numeric_claims` against sealed versions only (`0012:294-305,472-475`);
  versions lock `REPORT_VERSION:<id>` (`0012:280-291`). Imports run as panel.
- **Evidence grants.** `put_capture_ref` INSERTs on its repository's pool
  (`evidence/repository.py:239-248`); owner has SELECT only on evidence tables (`0012:478-486`).
- **Shared tests.** Manifests are globbed, mapped and dispatched (`test_frozen_manifests.py:44,52-59,678-685`);
  generic `check_values` requires numerical readings (`:497-506`); the approved payload must exist in
  the e2e commit's parent (`:754-773`). An amendment record hashes its whole item list
  (`test_amendment_records.py:49-58`). `scripts/verify_project.sh:60` names the D7 exit test.

## Rulings (proposed; Sol approves with the plan)

- **R1 Paths.** Roadmap `0008_coverage.sql` → `0024_coverage_registry.sql` (D7.1),
  `0025_coverage_batches.sql` (D7.2), `0026_watchlist.sql` (D7.3). D7.4's record is a **new** file
  `docs/blueprint/amendments/2026-10-17-coverage-initiation.md`. No `coverage/watchlist.py` and no
  `coverage/batch.py`: decisions reuse `ledger decide`; batch orchestration of the command-level
  `onboard`/`run_compare` lives in `api/coverage_cli.py` (dependency direction `api → components`).
  The orchestrator edits the roadmap row when recording this plan.
- **R2 Owner role writes coverage.** Coverage tables: INSERT to `eqos_owner` only, SELECT to all
  three roles, `run_by` = `current_user`; the runtime role cannot launch a batch or pick coverage.
  `0024` also grants `eqos_owner` INSERT on `eqos.capture_refs` and USAGE on its sequence — nothing
  else in evidence or identity — so the owner CLI registers its captures via `discovery.store_captures`.
  Onboarding and comparison inside a batch keep their runtime pools.
- **R3 Verified and captured = admitted (`ONBOARDED`/`PARTIAL`) result of a completed batch,** pinning
  the onboarding record and same-entity run it consumed. An `INCOMPLETE` comparison counts; an
  unfinished batch does not.
- **R4 Replay.** `coverage batch --raw-root <dir>` replays `<dir>/<SYMBOL>/gen-<n>/` through D6 — the
  bounded D7 exit path. The live-acquisition gap stays in the phase record; Q2 lands before the pilot.
  D6's freeze protocol is unchanged.
- **R5 No screen requests.** The coverage path makes no network request (socket guard). Legacy
  `screener-screen` refuses before any credential or network path; deleting its acquisition
  subsystem is a follow-up bead (touches `eqos-kx4.5`).
- **R6 Drafting gate.** "Drafting" = a runtime-role insert of a report version **or** of version
  content (`import_sources`, `report_sections`, `numeric_claims`); one predicate,
  `eqos.watchlisted(entity)`, gates both. A version insert also needs the report to be a
  `BOOTSTRAP_THESIS` or the entity to have an existing bootstrap **version** (database-stamped
  `created_at`); a bare report header does not count. Q4 ruling: an approved bootstrap is not
  required to *draft* — the spec requires the first initiation to be a bootstrap and its approval
  before initiation counts as approved, not before later drafting. Panel imports and sealed history
  are untouched.
- **R7 Serialization.** Owner decisions take the `WATCHLIST:<entity>` subject lock; the drafting
  triggers take it **first** (names sort ahead of `record_version`/`check_version_seal`, so order is
  always `WATCHLIST` → `REPORT_VERSION`) and read eligibility only after it. Runtime drafting refuses
  isolation other than READ COMMITTED (`a_memory_read_committed` precedent, `0019:60-72`), so
  post-lock reads see the committed head; timestamps come from `store_now()` after the lock.
- **R8 Members.** Batch **ETERNAL, POLYCAB, TITAN**; others **THERMAX, CGPOWER** — all `PARTIAL`
  in the v2 smoke (THERMAX `gen-3`, rest `gen-1`), formerly phrase-free (D7 → D6b). ETERNAL has a
  real former NSE symbol (ZOMATO). Not chosen: APARINDS (`eqos-g2q`), SONACOMS (dropped 2026-10-14),
  NETWEB/HFCL/MTARTECH (not admitted). Input integrity is verified; current outcomes are not (preflight).

## Tasks

### Task 1: Universe registry and idempotent refresh

Goal: a retained instrument snapshot yields the expected rows; replaying it changes nothing; an
ISIN observed under a new symbol records a candidate event, becomes the current attribute, and
leaves the identity layers unchanged.
Stage: eqos-3oq.1
Files: Create `0024_coverage_registry.sql`, `coverage/__init__.py`, `coverage/registry.py`,
`api/coverage_cli.py` (`registry`), `tests/fundamentals/coverage_support.py`; Modify
`api/cli_parser.py`/`cli.py`; Test `test_coverage_registry.py` (`pg`, `retained`).
Interfaces:
- Consumes: `read_instrument_catalog`, `UpstoxInstrument`; `discovery.store_captures` on the
  registered `UPSTOX_INSTRUMENTS` surface (owner pool, R2); `identity_layers.latest_slice`.
- Produces: `load_registry(pool, instruments: Path, snapshots: SnapshotStore) -> RegistryLoad`
  (`load_id`, `created: bool`, `new_listings`, `candidate_events`); `eqos.registry_view`; CLI
  `fundamentals coverage registry --instruments <json.gz> --snapshot-root <dir>`.
Approach: a load is identified by its capture reference (the retained snapshot), not its bytes.
Replaying an already-loaded snapshot returns `created=False` and writes nothing; a genuinely later
capture with identical bytes is a new load. Per load: one load row, the capture, new stable
listings, one sighting per listing carrying the observed symbol/token/name. For each listing whose
observed symbol differs from its sighting in the **preceding** load, one candidate event. Current
attributes, status and last-seen derive from the latest sighting in the view.
Verification: `uv run pytest tests/fundamentals/test_coverage_registry.py`, loads through the
public owner CLI — the 2026-09-04 snapshot gives the aid's 7,845 listings and spot rows; replay
returns `created=False`, counts unchanged; a later capture re-marking ETERNAL → `ZOMATO` (SYNTHETIC,
`tmp_path`) yields one candidate event with ZOMATO current; another capture of those bytes adds no
event; a later capture of the original bytes restores ETERNAL with one more event; identity events,
relationships, base rows and `latest_slice` never change; runtime INSERT is refused.
Dependencies: None.
Risks: decoded list ~55 MB, loaded once per module; re-marked snapshots never committed.

### Task 2: Screens, screen runs and capture batches

Goal: a five-member CSV resolves; a completed batch over three members onboards and compares
exactly those three, the other two have nothing; no network request; nothing scheduled; the legacy
screen command refuses.
Stage: eqos-3oq.2
Files: Create `0025_coverage_batches.sql`, `coverage/screens.py`, `fixtures/coverage/screen_export.csv`;
Modify `api/coverage_cli.py`, `api/onboard_cli.py`, `api/compare_cli.py`,
`api/screener_cli_dispatch.py`, `contracts/source_catalog.py`, `contracts/canonical.py`; Test
`test_coverage_batch.py` (`pg`, `retained`).
Interfaces:
- Consumes: `registry_view` (Task 1); D6 replay; `compare_command`.
- Produces: `record_screen_run(pool, screen_text: str, csv: Path, snapshots) -> ScreenRun` (`run_id`,
  `members`, each `listing_id: int | None`, `reason: UnresolvedReason | None`); `declare_batch`,
  `record_member_result`, `complete_batch` in `coverage/screens.py`; `onboard_cli.onboard(symbol,
  raw_root, snapshot_root, config_root, generation=None) -> Onboarded` (`outcome`, `entity_id`,
  `onboarding_record_id`, `compare: str | None`, `exit`); `compare_cli.run_compare(args) ->
  RunRecord`; CLI `coverage screen-run --screen <txt> --csv <csv> --snapshot-root` and
  `coverage batch --screen-run <id> --members A,B,C --raw-root --snapshot-root [--config-root]`.
Approach: the screen definition is stored once by text hash; the CSV as a `SCREEN_EXPORT` capture.
Resolution against current registry attributes: both codes supplied → each must resolve and agree
on ISIN, else `UNRESOLVED` (`CONFLICTING_CODES`); a supplied NSE code that matches nothing →
`UNRESOLVED` (`UNKNOWN_NSE_CODE`), no BSE fallback; NSE code absent → BSE code alone; zero or several
matches → `UNRESOLVED`. `coverage batch` refuses any symbol that is not a resolved member with an NSE
listing (nothing written), then declares the batch with the chosen screen-member ids in one insert,
and per member calls `onboard`, runs the printed command through `run_compare` when admitted, and
records a terminal result pinning the onboarding record and run. The database refuses a result
whose run, onboarding record and member entity differ, or whose entity's verified ISIN is not the
listing's. When every declared member has a terminal result, it appends the completion; an
interrupted batch stays incomplete. `_onboard` and `_run` become thin printers over the extracted
functions. `screener-screen` raises a refusal at dispatch, before settings or credentials load.
Verification: `uv run pytest tests/fundamentals/test_coverage_batch.py` — five members resolve; a
TITAN-NSE/POLYCAB-BSE row is `UNRESOLVED` and refused before any batch write; a batch over ETERNAL,
POLYCAB, TITAN (pinned copies in `tmp_path`) completes with three `PARTIAL` results, each with a
same-entity run of nonempty comparison rows; THERMAX and CGPOWER have no onboarding record, capture,
entity or run; another entity's run link is refused; a batch stopped after one member has no
completion; `fundamentals screener-screen …` refuses; patched `socket.socket.connect` is never
called; `fundamentals.coverage` imports no `sched`, `threading`, `asyncio`, `subprocess` or
`ingest.screener_screen`. `test_data_stage4_e2e.py` and `test_onboarding_acquisition.py` stay green.
Dependencies: Task 1. Preflight (orchestrator, before dispatch): at `HEAD`, on a scratch
`eqos_test_*` database, replay the five generations with `fundamentals onboard` and confirm
`PARTIAL`, then run the printed comparison for ETERNAL, POLYCAB, TITAN and confirm a stored run
with comparison rows (`ad29c3e` landed after the smoke).
Risks: until Q1 is met the CSV uses a `SYNTHETIC-FORMAT` header, for development only; no
provisional e2e is committed in this task. Three onboardings cost minutes; one module database.

### Task 3: Watchlist decisions and the drafting gate

Goal: `ADD`/`REMOVE` are owner-only with a verbatim ruling; adding an unverified, uncaptured or
unfinished-batch stock is refused; runtime drafting or content for a stock off the watchlist is
refused, including after `REMOVE`; a new member's first version must be `BOOTSTRAP_THESIS`.
Stage: eqos-3oq.3
Files: Create `0026_watchlist.sql`; Modify `contracts/ledger.py`, `ledger/lifecycle.py`,
`tests/fundamentals/coverage_support.py`, `ledger_support.py`, `memory_support.py`,
`test_ledger_stage{1,2,3}_e2e.py` (seed only); Test `test_coverage_watchlist.py` (`pg`).
Interfaces:
- Consumes: `batch_member_results`/`batch_completions` (Task 2), `store.insert_decision`, `ledger decide`.
- Produces: `SubjectKind.WATCHLIST` (subject id = entity id), `DecisionKind.ADD`/`REMOVE`;
  `eqos.watchlisted(entity bigint) RETURNS boolean` (also D9.2's covered-stock test);
  `eqos.watchlist_digest(entity)` = SHA-256 over the entity's latest admitted result in a completed
  batch (completion, result, onboarding record and run ids), NULL if none; test helper
  `watchlist(pools, entity_id)`.
Approach: `TRANSITIONS` gains `ADD` (owner; head `None` or `REMOVE`) and `REMOVE` (owner; head
`ADD`). `check_owner_watchlist` mirrors `check_memory_decision` and is named to sort before
`check_panel_review` and `stamp_decision`: it derives and sets the decider from the role (owner
only), refuses a stale head and an empty ruling, and sets `sealed_digest =
eqos.watchlist_digest(subject)`; a NULL digest makes `store.subject_digest` raise first, so
refusals hold in both layers. `a_check_drafting` implements R6/R7 on `report_versions` and the three
content tables. Characterization first: apply 0026, run the ledger, memory and views suites, list
what breaks, then seed shared fixtures. Seeds write each row through its owning role (runtime
onboarding record and run; owner batch rows and `ADD`), never migrator authority or disabled
triggers; historical e2es reuse their imported bootstrap versions. D5's frozen exported and reader
inventories (`test_ledger_stage3_e2e.py:184-196,230-236`) must not change — if a seed would, stop
and report.
Verification: `uv run pytest tests/fundamentals/test_coverage_watchlist.py` — owner `ADD` via
`store.insert_decision` with no supplied decider accepted; empty ruling, runtime and panel
`ADD`/`REMOVE` refused; no onboarding record, never batched, and unfinished batch refused; `REMOVE`
then re-`ADD` legal; runtime version off the watchlist refused; section and claim into a version
created before `REMOVE` refused after it; runtime content into a panel-created unsealed off-watchlist
version refused; bootstrap header without version then `EARNINGS_UPDATE` refused; bootstrap version
then `EARNINGS_UPDATE` accepted; off-watchlist panel import accepted; two connections, a draft that
saw `ADD` versus a committing `REMOVE`, end with the draft refused. Then
`uv run pytest tests/fundamentals -k "ledger or memory or views"` green.
Dependencies: Task 2.
Risks: wide blast radius (every runtime draft in D3–D5 tests); mitigated by shared seeds.
