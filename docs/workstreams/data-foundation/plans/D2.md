**Goal:** Import the legacy SQLite fact store into PostgreSQL losslessly. Then:
- serve the `FactStore` contract from PostgreSQL;
- admit first-party facts by the §4 policy;
- render filed tax and the headline PBT per §1 on both report paths;
- prove matched backup and restore, including onto a fresh instance;
- prove cutover and the frozen-window rollback.

All of it is rehearsed on test databases.

**Out of scope:**
- Production import and cutover of `equity_os`. That is bead `eqos-3zl`: owner-gated, it must
  precede the pilot (PILOT-3) (ruling R2). This plan ends at the runbook.
- Rollback after PostgreSQL writers reopen. It is not supported; recovery is verified backups plus
  forward repair (ruling R1).
- Retiring the legacy files.
- Retention classes, purge, "retained-only" backup and expired-capture handling (D9; ledger §6
  items 5, 6 and 9).
- Off-machine backup destinations (spec Out of Scope).
- Binding every new fact revision to producer identity. Only admitted facts bind run identity; the
  rest of `eqos-unv` stays open.
- Porting fact-store consumers that are not named in a Verify cell (ruling R3, OQ9).

**Constraints:**
- "Tests use their own test database, never the main one" (spec §6). Every PostgreSQL task runs
  on `eqos_test_*` databases (`tests/fundamentals/pg_support.py`). No task or test touches the
  `equity_os` database or the live Postgres data directory.
- Tests read the legacy SQLite file only as a copy in `tmp_path`, pinned by SHA-256
  `cb02b0f12a1708d07f4e8f1dbaefd59bb89762897b6de242c03da9f9a8157bd8` (`retained` marker).
- "Each file is opened read-only, never through the store's initialising constructor, and
  fingerprinted (SHA-256)" (spec §6 step 2).
- "No identity is recomputed" (spec §6 step 3). The following are preserved byte for byte:
  - row ids, content identities and value hashes;
  - revision families and ordinals;
  - canonical status and selection timestamps;
  - selection ids, sequences and predecessor links;
  - stored digests and legacy-baseline flags.
- Evidence tables are immutable: triggers reject UPDATE, DELETE and TRUNCATE, and the runtime role
  has SELECT and INSERT only (spec §6). This covers imported legacy facts, selections, admissions
  and store events.
- "Revision ordinals and selection sequences are allocated under a row lock or serialisable
  isolation with predecessor checks, retrying serialisation failures at most three times, then
  failing loudly" (spec §6).
- Store time comes from the monotonic `eqos.store_now()`. A transaction that takes
  `eqos.lock_queue()` must do so before its first `store_now()` (D1b, migration 0009).
- Approval means Sol's (`gpt-6.1-sol`) `APPROVE`, recorded as reviewer, verdict, date and payload
  SHA-256 (roadmap Conventions).
- Any gated mutation of a database whose name does not start with the literal `eqos_test_` also
  needs the owner's authorization record; restore to such a name is refused outright (Design
  decision 6).
- The frozen Stage 2 manifest is hand-authored from source bytes, approved and committed before
  `test_data_stage2_e2e.py` exists.
- Stage 1 suites stay green after every task: `test_data_stage1_e2e.py`, `test_frozen_manifests.py`
  and `test_compare_tracer.py`.
- Migrations are forward-only and additive, numbered from `0010`. This plan adds `0010` and `0011`.
- Python rules:
  - `mypy --strict` and ruff;
  - frozen Pydantic models and enums;
  - structlog, never `print`;
  - files ≤800 lines. `api/pipeline.py` is already 848 lines and must not grow (net ≤ 0).
- Minimal code (owner, 2026-10-14):
  - every module traces to a Verify cell;
  - the import is a bounded raw-table copy with complete row comparison, with no migration
    framework;
  - reuse the existing pool, settings, intake, CLI registration and test support.
- Test policy:
  - characterization first;
  - integration over the real legacy file and retained captures;
  - the e2e orchestrates the same operations rather than re-checking them;
  - unit tests only for the gate rule and the digest/chain rule;
  - gate and refusal cases are one parametrized table per test file over a shared setup fixture;
    operation-specific integration checks stay separate tests.
- **Per-task gate** (finding 21). Before dispatching the implementer:
  - new-behaviour tasks run `scripts/verify.sh red d2-<N> <task test targets>`;
  - the characterization and refactor task runs `scripts/verify.sh baseline d2-1`.

  Each task ends green on `scripts/verify.sh gate d2-<N>`, which runs:
  - `uv run ruff check src tests/fundamentals`;
  - `uv run ruff format --check src tests/fundamentals`;
  - `uv run mypy --strict src`;
  - `uv run pytest tests/fundamentals`.

  That last target includes the Stage 1 trio. The gate also runs the red-proof, skip-guard,

## Design decisions fixed by this plan

1. **One PostgreSQL store beside the SQLite one.**
   - `store/pg_fact_store.py:PgFactStore` implements exactly the `FactStore` public methods:
     `put`, `select_canonical`, `get_revisions`, `get_selection_history`, `get_canonical`,
     `query_canonical`, `content_identity_for` and `close`. It adds one method, `fact_ref`.
   - Both classes satisfy a new `FactStoreLike` Protocol, and the consumers' annotations move to
     it.
   - Task 1 lifts the digest, chain-check and cutoff rules into module-level pure functions, and
     both classes call them.

2. **Unambiguous ids: store-local handles plus origin-qualified refs** (finding 1).
   - Every row and selection in PostgreSQL has a target store, a **store-local handle**
     (`bigint`) and a preserved **origin-qualified ref** `(origin, origin_id)`.
   - The public `int` ids in `StoredRevision.row_id`, `CanonicalSelection.selection_id` and
     `predecessor_id` are the handles of the store the instance is scoped to. The same holds for
     `select_canonical(row_id, expected_selection_id=…)`.
   - **Imported rows:** handle = origin_id = the legacy id, and origin = the legacy origin id.
     The SQLite-visible ids are therefore unchanged.
   - **Native rows and selections:** origin = `pg-native` and origin_id =
     `nextval(eqos.fact_native_id)`, one sequence for both. The handle is the store's next free
     handle, so `(pg-native, 1)` coexisting with legacy `(sqlite-…, 1)` gets handle 44, never 1.
   - The selection digest keeps the legacy payload over handles, so one `verify_chain` checks
     imported and native chains alike.
   - `fact_ref(row_id) -> FactRef(store_id, origin, origin_id)` returns the preserved ref. On SQLite
     it returns `(store_id=<db path label>, origin="sqlite-local", origin_id=row_id)`.

3. **Stores are namespaces.**
   - `eqos.fact_stores` has one row per store: kind `LEGACY_SQLITE` (with fingerprint and file
     label) or `NATIVE`.
   - The legacy origin id is `sqlite-` + the first 16 hex characters of the file SHA-256.
   - A `PgFactStore(pool, store_id)` reads and writes only rows whose target is `store_id`, so
     two stores with identical ids or identities never merge.

4. **Pre-selection-schema files** (ruling R3, OQ1).
   - The importer reproduces `_migrate_legacy_selections` exactly:
     - selection ids in `row_id` order of canonical rows, starting at 1;
     - sequence 1 and no predecessor;
     - `selected_at` = the stored `canonical_selected_at` text;
     - reason = the stored reason;
     - `legacy_baseline = true`;
     - the lifted digest.
   - Those rows are flagged `synthesized = true`. Two refusals apply:
     - a canonical row without `canonical_selected_at` is refused (`NO_BASELINE_TIME`);
     - two canonical rows in one family are refused (`MULTIPLE_BASELINES`).
   - A file that already has `canonical_selections` is copied verbatim.

5. **Bytes, not types.** `fact_json`, every timestamp, `anchor` and `canonical_reason` are stored as
   the exact SQLite text. Native timestamps are written in the same `datetime.isoformat()` form.

6. **One gate for every mutation** (findings 4, 12). `pg/approvals.py` holds it.
   - **Sol approval.** The approved file is a YAML artifact plus one line `approval: {reviewer,
     verdict, date, payload_sha256}`. The payload is the file's bytes without that line.
   - **Owner authorization.** A separate YAML record `{by, date, database, operations,
     approved_payload_sha256}`. It names the Sol-approved payload's hash, so it never changes that
     hash; it is an operational attestation. Each record binds exactly one payload, so production
     uses two records (blocker 3):
     - the **import record**: `operations: [IMPORT]`, payload = the approved preflight, which
       itself binds the manifest payload SHA-256;
     - the **transition record**: `operations: [CUTOVER, REOPEN, ROLLBACK]`, payload = the
       approved reconciliation report.
   - `check_gate(op, *, database, approval, owner)` is pure. `database` is a test database only
     when it starts with the literal `eqos_test_` and matches `^[a-z_][a-z0-9_]*$`. The setting's
     prefix is never consulted.
     - **Test database:** the reviewer may be `gpt-6.1-sol` or `test-fixture`; the owner record is
       optional.
     - **Any other database:** the reviewer must be `gpt-6.1-sol` and the owner record is
       required. Its `database` must equal `database`, `op` must be in its `operations`, and its
       `approved_payload_sha256` must equal the approval's.
   - `authorize(conn, op, approval_path, owner_path)` runs `current_database()` on the
     **connection the operation will use**, then runs `check_gate`. It also checks that the
     payload's recorded database identity (name; host and port of the settings that built the
     pool) equals the actual one.
   - `GatedOperation` is `IMPORT`, `CUTOVER`, `REOPEN` or `ROLLBACK`. All gated operations call
     `authorize` before their first write. `IMPORT` checks the manifest's and the preflight's Sol
     approvals and the preflight's recorded manifest SHA-256; its owner record must cite the
     preflight's payload SHA-256.
   - The payload must be **rechecked inside the committing transaction**: the operation
     recomputes its payload on the same connection and refuses `APPROVAL_STALE` unless it equals
     the approved bytes. That is the binding to manifest, database identity, translation pins and
     verified binding set.
   - **Restore is test-target-only in D2** (blocker 2) and is not a `GatedOperation`. Before any
     connection, the requested name must pass `is_test_database` and the moved test-DB name guard;
     the database is created through the guarded test-DB path, and the restore then checks
     `current_database()` on its own connection equals the requested name. Restoring onto a
     non-test name is refused with no override. A production restore is an owner-authorized
     procedure in `eqos-3zl`'s runbook, not D2 code.

7. **Fact-store state machine** (findings 15 and 3/14 under R1). `eqos.fact_store_events` is
   append-only, and a store's state is its latest event.

   | From | Operation | To | Checks |
   |---|---|---|---|
   | (none) | `import` | `IMPORTED` | Design decision 6; lossless verify |
   | `IMPORTED`, `ROLLED_BACK` | `cutover` | `CUTOVER_FROZEN` | approved reconciliation rechecked; legacy fingerprint unchanged |
   | `CUTOVER_FROZEN` | `reopen` | `OPEN` | — |
   | `CUTOVER_FROZEN` | `rollback` | `ROLLED_BACK` | no row or selection beyond the latest `CUTOVER_FROZEN` event's last handles; legacy fingerprint unchanged |
   | (none) | `create_native_store` | `OPEN` | — |
   | `OPEN` | `rollback` | refused | `ROLLBACK_WINDOW_CLOSED`: recovery is backups plus forward repair |

   Any other (state, operation) pair is refused `ILLEGAL_STATE`. Rollback exists only inside a
   cutover window, so it always has a marker; `IMPORTED` has no rollback (blocker 4).

   Rules that apply across the table:
   - `PgFactStore` writes are accepted only in `OPEN`, so an imported store refuses writes until
     cutover and reopen.
   - In every other state a write raises `FactStoreFrozenError` and persists nothing. That
     includes a stale `PgFactStore` instance after rollback.
   - Routing via `open_fact_store`, by state:
     - `OPEN` opens `PgFactStore`;
     - `ROLLED_BACK` opens SQLite `FactStore` on the issuer config's `store_db`;
     - `IMPORTED` and `CUTOVER_FROZEN` are refused (writers frozen);
     - a config without `fact_store_id` keeps today's SQLite behaviour.
   - Each operation takes the manifest's full store set and writes one event per store under one
     operation id, all in one transaction. A multi-store transition completes atomically or not
     at all.
   - Repeating an operation whose stores are already in the target state is a no-op that returns
     the existing operation id.
   - **Legal recovery commands per state.** `legacy status` prints the state and exactly these:

     | State | Legal next commands |
     |---|---|
     | `IMPORTED` | `legacy reconcile`, then `legacy cutover`. To abandon instead: restore legacy write permission. No issuer config routes to the store (`fact_store_id` is added only at reopen), and once the legacy file changes, cutover is refused (`FINGERPRINT_CHANGED`); a later attempt imports with `new_import: true`. |
     | `CUTOVER_FROZEN` | `legacy reopen` (PostgreSQL authoritative) or `legacy rollback` (SQLite authoritative) |
     | `ROLLED_BACK` | `legacy reconcile`, then `legacy cutover` (same report bytes while the legacy file is unchanged; refused `FINGERPRINT_CHANGED` after any SQLite write, then as abandon above) |
     | `OPEN` | none; recovery is verified backups plus forward repair |

8. **Consumer tax and headline PBT come from the pipeline's own first-party read** (findings 10,
   2; ruling U1).
   - Admission is `AGREE`-only (finding 7), and Apar Q2 tax and headline are
     `AGREE_UNQUALIFIED`, so neither can be admitted.
   - The pipeline already renders its six roles from its own XBRL parse. Composition appends two
     optional report operands (`required=False`, qualified with the config's `taxonomy_prefix`) to
     the resolved `concepts.aux` whenever they are not already listed, so issuer configs that
     declare their own `aux` (Apar does) receive them without config edits (issuer config bytes
     are digest-pinned by approved intakes):
     - `<prefix>:TaxExpense`;
     - `<prefix>:ShareOfProfitLossOfAssociatesAndJointVenturesAccountedForUsingEquityMethod`.
   - Verified on the retained Apar Q2 FY26 case through the real `config/aparinds-fy26-q2.yaml`
     (prefix `in-capmkt`), with no test-only operand injection: tax, ETR and headline render
     values, not `OPERAND_MISSING`.
   - It renders four labelled lines through one shared helper (`output/pnl_lines.py`, also used
     by `report_builder`):
     - `Tax expense (filed, ₹ crore)`;
     - `Effective tax rate (%)` = filed tax ÷ `profit_before_tax` × 100, quantized 0.01;
     - `Headline PBT incl. associates (₹ crore)` = `profit_before_tax` + share of associates/JV
       (§1: XBRL does not report the headline separately);
     - the role fact line relabelled `Profit before tax (before share of associates/JV)`.
   - A missing filed tax renders `OPERAND_MISSING` for tax and ETR. A missing share of associates
     renders `OPERAND_MISSING` for the headline. PBT − PAT is never computed on either path.
   - The admitted-fact read API (`admission.read_selected`) exists and is proven on admitted
     `AGREE` cells; it does not feed the D2 report.

9. **Concurrency** (finding 13). Every `PgFactStore` write and every admission runs at
   `SERIALIZABLE`, in this statement order:
   1. `SELECT eqos.lock_queue()`, the existing store-clock write lock, before any `store_now()`;
   2. read the store state;
   3. read the identity head (`put`: existing row and max ordinal; `select_canonical`: chain
      head);
   4. call `store_now()` once;
   5. insert.

   DB constraints carry the invariants:
   - `UNIQUE(target_store, content_identity, value_hash)`;
   - `UNIQUE(target_store, content_identity, revision_ordinal)`;
   - `UNIQUE(target_store, content_identity, sequence)`;
   - `UNIQUE(target_store, content_identity, selected_at)`;
   - `UNIQUE(target_store, predecessor_handle)` (non-forking);
   - `CHECK((sequence = 1) = (predecessor_handle IS NULL))`;
   - same-store FKs for the row and the predecessor.

   Serialisation failures (40001, 40P01) are retried at most three times, then
   `FactStoreRetryError` is raised. Two more read rules:
   - Multi-family reads (`query_canonical`) run in one `REPEATABLE READ READ ONLY` transaction.
   - The default cutoff is `compare.queue.overlay_boundary(pool)`, taken before that transaction,
     so every write stamped at or before it has committed.

10. **pg_dump and pg_restore run from the pinned image** (ruling R3, OQ8):
    `docker run --rm --network host -e PGPASSWORD postgres:18.6 …`. The password comes from the
    injected environment, never argv; the client prefix is an injected argument.

11. **Recreation and fresh-instance checks run on uniquely owned compose projects** (finding 5;
    Task 8 lists the script's guards).

   2. Check that it equals the rehearsal's except for database identity.
