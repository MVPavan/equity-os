Equity-OS Architecture of Record

The system we intend to build, drawn only from the 25 written specifications (S01–S25), the v2 decision register, and the component ledger. Every claim below traces to a spec. Nothing is invented; where the specs deliberately leave something open, this page says so.

It adds §5 Day in the life — the concrete operating loop of one quarter review — §7 Data sourcing strategy as an explicitly proposed direction awaiting your decision, and §8 Toolchain, which separates required capability from implementation choice and marks every unfixed choice TBD. 1

What it is, in one breath

Equity-OS is a persistent, evidence-governed equity-research system for Indian listed companies — not an autonomous stock-picking chatbot. Its operating doctrine (S01, CONTEXT.md):

SQL records what happened. Curated memory preserves what was learned. Deterministic code calculates implications. Agents investigate, challenge, and explain. Execution remains separately controlled.

Who uses it: a small internal research team — a solo builder plus an accountable analyst / product-owner role. Posture is private/internal research only; every other mode (public, paid, personalized, execution-connected) is prohibited by default (S01).

The first product deliverable is a fixed earnings-review workflow (S14): given a company's new quarterly results and an approved prior thesis, produce a reviewable, source-backed update showing what changed in facts, management commitments, calculations, uncertainties, and thesis — every material statement traceable to a source, a calculation trace, or a fact.

How it will be proven out: one discovery company across four consecutive quarters (S05) — quarter 0 done manually as a baseline, quarters 1–3 done with the system — measured on analyst review economics: minutes per approved update, corrections needed, time to locate sources (S18, S08).

5

Day in the life — one quarter review, end to end

The same fixed loop, told as work rather than as a diagram: what starts a run, what the analyst does, what the system does, and what immutable record each step leaves behind. Reconstructed from S09, S11, S14, S15, S06, S13 and S16.

What triggers a run

A person does. A quarter review starts when the company's new quarterly-result package exists and the analyst decides to review it. Nothing schedules or scopes a run on its own: the run is registered explicitly with a company, a quarter, a source package, a knowledge cutoff, and the exact preceding approved thesis (S14 §4.1). Quarter 1 consumes the approved Quarter 0 thesis; Quarters 2 and 3 each consume the approved preceding one — a draft or unapproved thesis blocks registration outright.

Two things run before and outside any review: daily and event-driven point-in-time capture of prices, announcements, corporate actions, shareholding and membership changes (S09 · B-09), and the immutable document registry (S09 · C-02). They persist successes and failures continuously, so that when a run is registered the evidence it may see already exists with hashes and first-seen times. Capture is not a research decision and produces no analysis.

If it crashes — recovery and resumption

State is never held in memory or asserted by a model. The current step is derived from one valid genesis followed by a hash-chained series of transition records; if the process dies, the run is exactly where its last committed record says it is.

  • A failed step records where it must resume. A failure is written as its own transition preserving the target it was trying to reach, and may later resume only into that exact target. A blocked step does the same and stays blocked until its recorded blocker is resolved.
  • Retries never duplicate. Each attempt carries an idempotency key derived from the step, workflow version and exact input digest. Repeating the same key returns the already-committed output or safely completes the same commit; changed inputs require a new key and a new output. Crashing before, during, or after commit still yields exactly one output and no duplicated side effect.
  • Nothing partial becomes usable. An attempt that fails its final authorization or validation check is recorded as failed and its provisional output is not consumable.
  • The cutoff survives. Resumption never changes the run's knowledge cutoff, and post-cutoff evidence cannot enter a later evidence-package version. A different cutoff is a different run.
  • What the analyst sees: the run sitting at its last committed step; which step failed or is blocked, with its failure stage, code and detail or its named blocker; the exact step it will resume into; which outputs survived and which were invalidated; and — after resume — that the work reran only where it had to. A re-drafted narrative comes back as a new artifact requiring review, never as proof that the old one was reproduced.
What is deliberately absent from this loop. There is no planner, no scheduler that decides what to research, and no agent-selected transition. Every step is either a registered step executing against a sealed evidence package or a typed human decision; the legal edges are a closed set, and anything outside it blocks. Source text is data and cannot select a transition, a tool, a cutoff or an outcome. Agents draft, extract, classify and explain — they never approve, promote, publish, or compute an authoritative number. S14 non-goal DEF-03

7

Data sourcing strategy — a proposal for your decision

Where the facts come from is not settled by the specs. This section states one proposed direction and the rules that would govern it. It is not architecture of record, and approving this page does not adopt it.

Status · proposed, not accepted

This is a proposal awaiting your decision, not a decision already made. The specs deliberately leave the sourcing shape open: A-05 owns provider rights and A-06 owns the XBRL-versus-PDF coverage spike, and neither is accepted. Everything below is conditional on you choosing it — and on the A-06 evidence, which does not exist yet.

No vendor, feed, parser, extraction library, or model is selected here or anywhere in this document. Nothing in §7 may be read as a commitment to buy, install, or integrate anything.

Tier 1 · proposed primary

Official structured sources first

Official structured/XBRL payloads — exchange quarterly-result XBRL and structured annual channels where available — are the first and preferred source for every measurement the structured channel actually covers.

Filing channel and taxonomy name/version are recorded independently per observation; issuer-hosted is a channel, not a claim that its document is structured.

Tier 2 · proposed gap fill

Official PDF extraction for what Tier 1 misses

Where the structured channel demonstrably does not carry a statement, segment, note, ownership/share-count item or restatement case, official PDFs and other unstructured documents — including issuer-hosted PDFs when used for extraction — are extracted with exact page, table and offset provenance back to the original bytes.

Which measurements fall here is an output of the A-06 spike, not an assumption made in advance.

Tier 3 · proposed cross-check only

A licensed vendor feed, as reconciliation only

If — and only if — the source-rights record permits it, a licensed vendor feed is used solely to cross-check what Tiers 1 and 2 already produced. It is never the primary source of a fact, never fills a gap on its own, and never becomes authoritative because a vendor produced it.

If such a feed carries consensus estimates, those remain excluded by default and need their own proof of licensed and necessary C-13 · DEF-07.

Rights and authorization come first

No tier is reachable without its own rights record across the ten independent dimensions — access, automation, caching, retention, commercial use, derived outputs, redistribution, account limits, point-in-time availability, replacement path. Permission to look never implies permission to automate, cache, retain, derive from, or redistribute; private permission never implies public. Missing or ambiguous rights resolve to UNKNOWN, and unknown denies the operation. S02 · A-05

Acquisition binds one current authorization snapshot; parsing or re-extraction binds a separate current authorization, revalidated immediately before the parser runs and again before the output may be used. Renewal appends a new snapshot; it never silently refreshes an old one. A vendor feed adds a provider-authorization requirement that cannot default to "not required". S09 · S02

Immutable bytes, and a first-seen time that cannot be faked

Every tier's payload is stored as original bytes, content-addressed, with its URL, retrieval time and first-seen time. First-seen time is acquisition evidence — it can never be backdated to simulate point-in-time history. A run admits only records whose knowledge time is at or before its cutoff, so a source acquired later cannot leak into an earlier run.

This is the hardest limit on Tier 3: a vendor's deep history is not a substitute for point-in-time capture the system never performed. Buying history does not create the evidence that the system knew it at the time. S09 · S11

The coverage question is decided by evidence, not preference

The boundary between Tier 1 and Tier 2 is exactly what the A-06 spike measures: a matrix by company, quarter, filing channel, format, taxonomy version, statement, segment, note, ownership/share-count coverage, restatement behaviour, mapping stability and reconciliation effort. No aggregate score may hide a missing statement, segment, note, ownership or restatement case — and the spike explicitly does not declare either format universally authoritative. Until it runs, the tier split is a hypothesis. S09 · A-06 · R-2

When the tiers disagree

A disagreement is not a tie to be broken by preference. Each tier's value is an observation against the same measurement key; conflicting observations enter a revision family and get a recorded reconciliation decision with a typed reason — issuer restatement, source correction, parser re-extraction, manual correction, or normalization-policy change. Canonical selection is then resolved as of the run's cutoff.

Two rules do the work: "newest" is not a valid selection policy, and neither is "the vendor said so". An unresolved conflict is surfaced as a review item — and, where it touches something important, resolves to review required rather than to not material. Nothing is silently overwritten and no prior observation is deleted. S12 · S06

Fail closed, in named ways

  • Unknown or ambiguous rights → the fetch is denied.
  • No current transformation authorization → the parser is never invoked, and the rejection must prove it was not invoked.
  • A retrieval path that cannot prove cutoff behaviour → denied for authoritative use; any permitted exploratory response is quarantined and can never enter an evidence package, fact, claim, calculation or published artifact.
  • A capture failure is persisted as a failure with its stage and reason — never as "no event", and never as a silently missing row.
  • A gap that no permitted tier can fill stays an open question in the output. The system does not improvise a number.

Provenance survives every hop

Each observation keeps the exact parse attempt that produced it and the exact location — page, table, offset — inside the immutable bytes it came from, and the tier and filing channel it came through. A material claim resolves to a fact, a calculation trace, or an exact source location; the analyst reaches the original in one hop from the review screen. A cross-check that changed nothing is still recorded as a cross-check that happened. S09 · S12 · S13

Two things this proposal explicitly does not do

It selects nothing. No vendor, feed, XBRL parser, PDF extraction library, database, or model binding is chosen by this proposal; each would remain its own decision with its own rights and adoption gate.

It does not involve GBrain. GBrain is not used for sourcing, is not part of any tier, and is not a mandatory dependency of Equity-OS. Any memory engine remains an open, benchmark-driven decision. DEF-02 · S19 · S20

Your decision · under A-05 and A-06 Do you want this three-tier direction?

The realistic options are: (a) adopt the three tiers as the working sourcing direction, with Tier 3 still conditional on rights; (b) adopt Tiers 1–2 only and leave any vendor feed out of scope entirely; (c) defer the whole question until the A-06 coverage spike reports, and treat Tier 1 as the interim default; or (d) something else you name.

Whatever you choose changes only sourcing. It does not change the lineage rules, the fixed workflow, the human decision points, or the can/cannot lines — those hold for every tier, which is why the proposal can be decided separately from the architecture. Approving this page does not choose any of these options.

Outside dependencies and model rules

Data providers. Each source needs a rights record across ten independent dimensions; access permission never implies caching, retention, commercial use, derived outputs, or redistribution. Private permission never implies public. Consensus estimates are excluded by default (S02). Which sources are used is not settled — see the proposal in §7.

External tools. OpenBB and similar are dormant evaluation gates only. If ever adopted, they run out-of-process behind an Equity-OS adapter and still pass the rights gates; their outputs never become authoritative facts because a tool produced them (S03).

Where the LLM is — and is not — allowed. Agents may extract, classify, draft claims and narrative, select and explain an operator. They may not compute an authoritative number, convert one epistemic class into another, promote memory, or act on instructions found in source content (S16, S06, S12, S19, S07). Model and vendor bindings live in the project's role table, not in the specs.

Infrastructure. SQLite and simple state tables are the Phase-0.5 default. No workflow engine, database migration, or hosting platform is an architecture fact; each is reconsidered only on a measured trigger and a human decision (S10, DEF-13, SCALE-*).

Open decisions that touch the architecture

Three human decisions block all product code. They do not change the component set — each hardens the same pillar: hash-bound integrity of the evidence and approval chain.

HR-0001 — Output-approval evidence chain (S06)

Authorize one narrow documentation fix plus one fresh independent review so the earnings-output approval chain is cryptographically bound end-to-end — candidate output → materiality decision → disposition → inventory closure → published artifact → human approval — such that any upstream change invalidates every downstream commitment.

HR-0002 — Resolution-record integrity (S09)

Authorize a targeted fix plus fresh review so a recorded human resolution's identifiers must exactly equal the resolution it claims to come from — same review, same actor, same timestamp — with tests rejecting each mismatch.

HR-0003 — Approval import and correction ancestry (S10)

Authorize a targeted fix plus fresh review so approval records import completely and every correction chain is enforced as one unforked line back to a single current leaf, with digest-valid negative fixtures.

Also open by design (the specs leave these to evidence or to you):

  • Which discovery company and which four quarters (A-02).
  • The final output contract, the minimum fact/observation schema, the minimum claim schema — derived from the vertical slice, then amended into the specs.
  • The concrete materiality rules and every numeric success / budget / capacity threshold — human-approved, deliberately not in-spec.
  • The entity-source authority hierarchy (proposed, awaiting product-owner approval).
  • Memory engine choice; product name; any storage / workflow engine change.
  • The data-sourcing direction — the three-tier proposal in §7 is yours to accept, narrow, or defer under A-05 / A-06.
  • Every toolchain row marked TBD in §8.

Glossary

Observation
A typed, extracted, normalized value before reconciliation, with its exact source location.
Fact
A reconciled observation in the append-only, revision-aware store; restatements supersede.
Claim
A typed assertion (subject, predicate, object, scope, horizon, epistemic class, confidence); prose is display only.
Epistemic class
The mandatory label: observed / computed / inferred / forecast / opinion.
Evidence package
The frozen set of documents, facts and calculations a run works from; downstream steps fetch nothing new.
Knowledge cutoff
The latest knowledge time a run may observe; fixed before any retrieval; every query respects it.
Valid time / knowledge time
When a fact applies vs when the system could have known it — stored independently.
Point-in-time capture
Daily / event persistence with hashes and first-seen times; prevents future loss, never recreates the past.
Deterministic compute
Registered, traceable calculation code — the only authoritative calculator.
Calculation trace
Inputs, assumptions, operator version, replay class and output behind every computed number.
Thesis
The current approved analytical view of a company; versioned narrative; never a recommendation.
Management ledger
Tracked management promises: new / modified / due / outcome.
Observable falsifier
A named event, metric or outcome that would materially weaken or reverse a thesis impact.
Memory promotion
When separately activated, the distinct human decision that lets a draft change the canonical thesis. Agents draft; only the analyst promotes.
Golden set
Owned, expert-labeled evaluation fixtures (≥20 to start), grown from observed failures.
Review economics
The headline metric: analyst minutes per approved update, corrections, source-location time.
Distribution boundary
The hard gate between private research and any public / paid / personalized output.
Vertical slice
One discovery company across four consecutive quarters: Q0 manual baseline, Q1–Q3 assisted.
Artifact mode
Production, shadow-test, or golden-fixture. Only production artifacts can be approved toward publication or promotion; the other two are refused server-side.
Publication eligibility
A derived three-valued result — true / false / unknown. Only true publishes; missing, stale or ambiguous inputs give unknown, which blocks.
Rework
Routing a rejected or edited item back to the earliest affected step, creating evidence package v(N+1) and rerunning only the affected closure.
Resume target
The exact step a failed or blocked run may re-enter — recorded at the time of failure, never chosen afterwards.
